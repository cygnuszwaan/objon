# Objon — 2D tilemap puzzle-platformer (Godot 4.x, GDScript)

Godot 4.x, Compatibility renderer, GDScript only (no C#/.NET). Claude can run Godot 4.4 headless in its sandbox (the release zip downloads from github.com; wrap the project files in a minimal `project.godot` with the `Audio` and `Game` autoloads and the input actions, and run test scenes as the main scene, since `-s` scripts don't see the autoloads), which checks logic, signals and numbers but not rendering or feel — nothing here counts as verified until the user confirms it in their own editor.

## How to maintain this file

**This file describes the project as it currently stands, not how it got there.** It is not a changelog, a development diary, or a decision log. When something changes:

- **Update the relevant section in place.** Don't append a dated/numbered entry describing the change — rewrite the description of the system itself so it reads as if it had always worked this way. If a fix corrects an earlier bug, the bug and its history are not worth keeping once the fix is in and confirmed; just describe the correct behavior.
- **Only keep a pitfall if it's still a live risk.** A bug that's fixed and stable doesn't need a paragraph of "here's what went wrong and how it was diagnosed" — that's narrative, not a fact about the current system. A pitfall belongs in this file only if a future change could plausibly reintroduce it (e.g. "every hang-start function must set `hang_style` explicitly, or it leaks from the previous hang").
- **Prefer deleting over accumulating.** If a fresh read of the current code contradicts something written here, replace the claim — don't leave both the old and new version in the file "for context." If a whole section stops being true or useful, cut it rather than marking it stale.
- **Keep `export-audit.md` current.** It logs which scripts have been checked against the "runtime code never writes an export" rule (see Level editor seams). Update it whenever you audit or change an object, and add any new script to it. `audit_export_writes.py` re-runs the scan from the project root. It is the one deliberate exception to "describe the project as it stands": a work log that is deleted once the final pass is done.
- **When in doubt, ask: would a system prompt for this project want this sentence?** A system prompt states facts and constraints; it doesn't tell stories about how they were discovered. That's the target register for this whole file.

## Project setup

- Godot 4.x, Compatibility renderer (for touch/mobile support), GDScript only.
- Viewport 1280×720. `Camera2D` is a child of `Player`, zoom `4,4` (source art is 16px sprites; zoom rather than sprite scale keeps pixel-perfect rendering). Default Texture Filter is **Nearest**, set project-wide.
- **Script placement**: each `.gd` lives next to the `.tscn` it belongs to (e.g. `res://scenes/player/player.gd` beside `player.tscn`) — not centralized. `res://scripts/` is reserved for things that belong to no single scene (autoloads, shared helpers) — currently `Audio`, `Game` (an autoload holding the checkpoint snapshot and the respawn flow, handling `R` and owning the pause menu), and `LaserBeam` (`laser_beam.gd`, a stateless beam-solver helper used by every laser turret and every arc — see the laser bullet under World objects), and `MeltableBlock` (`meltable_block.gd`, the base class of the ice and metal blocks — see the Meltable block bullet under World objects), and `SurfaceTypes` (`surface_types.gd`, static helpers that define what a tile's `surface_type` means — see the Tilemap bullet), and `LevelCatalog` (`level_catalog.gd`, the playable levels as data, in play order — see Level loading under Checkpoint and save/restore). and `TouchControls` (`touch_controls.gd`, the on-screen controls `Game` adds as a child — see Touch controls under World objects).
- **Folder convention**: `scenes/{player,enemies,interactive,traps,levels,ui}/`, `sprites/` (subfolders per kind, `backgrounds/` for parallax art), `audio/`, `resources/` (`.tres` assets shared by more than one scene, tilesets included: a tileset used by several levels is saved here rather than embedded in each level, so every level shares the same tile data, `surface_type` custom data and collision shapes). `enemies/` = things with behavior/AI/health; `interactive/` = things the player acts on or rides (jump pads, conveyors, ladders, platforms, buttons, doors); `traps/` = things that act on the player (saw, crusher, spikes, cannon); `collectibles/` = things the player picks up.
- **Physics layers**: layer 1 = **actors** (any `CharacterBody2D` walking under its own `move_and_slide()` — Player, Drillbot); layer 2 = **world** (solid environment an actor can stand on or be blocked/pushed by — ground tilemap, `drop_platform`, `moving_platform`, `Crusher`'s `ArmBody`, `Cannon`'s `StaticBody2D`, `RotatingBody`). New actor: always mask layer 2; mask layer 1 too only if it should be solid against other actors (default: no, to avoid enemies pushing each other around). New solid platform/hazard body: layer 2, whether it moves or not. **Exception — anything the player should be able to kick (`Mirror`, `IceBlock`, `MetalBlock`) or bowl through with the surf (`BreakableBarrier`) sits on layers 1|2:** `KickHitbox` keeps the default mask (layer 1 only) and hits the target's physics body directly, and the bowl sweep queries layer 1 too, so a layer-2-only body is invisible to both; layer 2 keeps it solid like the rest of the world. Keep that pairing if either body's layers are ever changed. **Layer 0 with mask 2 = a body that collides with the world and that nothing else can see** (`Spark`: no query, sensor or contact filter on layer 1 or 2 finds it). **Layer 3 = the basin skim floor** (`WaterBasin`'s runtime one-way floor under a skimming surfer): only the player's mask includes it, so particles and blocks never see it. Pure-trigger `Area2D`s (gems, `Sawwheel`, `Crusher`'s root, `DrillHazard`, `KickHitbox`, `Bullet`) are unaffected — they stay on the default layer/mask unless they specifically need to detect something outside layer 1 (`Bullet` masks layers 1|2 so it also detects world tiles, not just the player). **`Area2D` never blocks movement, regardless of layer/mask** — it's a trigger only. A trap that also needs to be stood on (`Cannon`) needs a separate `StaticBody2D` on layer 2 for the solid part; the `Area2D` hazard, if any, is layered on top of that.
- **Groups in use**: `"player"` (added by `player.gd` in its own `_ready()`, not baked into `player.tscn`, so a node whose `_ready()` runs earlier in the level tree finds nothing: look it up again later, as `WaterManager` does every physics frame while its reference is null), `"trap"`, `"ground"`, `"catwalk"`, `"world_tilemap"` (the walkable ground `TileMapLayer`), `"ladder_tilemap"` (the separate ladder layer), `"water_manager"` (each level's `WaterManager` instance, looked up by basins/faucets/the player), `"water_solid"` (non-tilemap bodies water particles collide with and can be carried by — moving platform, drop platform, crusher's `ArmBody`, cannon's `StaticBody2D`, laser turret's and arc turret's `Body`, the laser receiver, the bullet target, the see-saw, the breakable barrier, ice blocks while intact), `"laser_mirror"` (every `Mirror`, and a see-saw with `mirror_surface` on; what `LaserBeam` iterates to find reflectors), `"power_target"` (every `PowerTarget`; how a conductor layer finds devices at its terminals), `"power_source"` (every button, speed trap, laser receiver, bullet target, weight plate, angle sensor and basin sensor), `"gem"` (every gem; the player counts the level's total from it at load), `"swing"` (every `Swing`; what the player's grab looks up), `"saveable"` (every node that takes part in checkpoint snapshots — see Checkpoint and save/restore), `"checkpoint"` (every checkpoint).
- **Tilemap**: `TileMapLayer` node (not the older `TileMap`). A `surface_type` String custom-data layer on the `TileSet` marks `"ground"`/`"glass"`/`"catwalk"` cells (glass: solid and unbreakable, ground-like for everything except light; it lives in its own atlas source in `ground_tileset.tres`, a full-tile collision shape on the world physics layer). **Nothing compares that string itself:** every question about it goes through `SurfaceTypes` (`is_ground_like()` (ground and glass), `is_catwalk()`, `is_hangable()` (ground-like or catwalk), `laser_passes()` (catwalk and glass), with `surface_at_cell()`, `surface_at_point()` and `surface_at_hit()` to read a tile's value; the hit version nudges half a pixel into the tile along the inward normal, so a hit on a right or bottom face maps to the right cell). The ledge grab, the catwalk-underside probe, the laser solver, the liquid and steam rays and the basin's floor and wall scans all use it, so a new surface type is added there and nowhere else. Bodies that aren't tiles opt in through the groups `"ground"` and `"catwalk"`, which each caller still tests itself. Ladders live on their **own** `TileMapLayer` (group `"ladder_tilemap"`, no collision — a ladder cell is just "a tile is present there"); a ladder shares its cell with the catwalk it passes through, top flush with the walking surface. One-way platforms use Godot's native `one_way_collision` shape property. The ground TileSet's other custom-data layers are `surf_friction` (float, see Surface friction under Surf) and `hazard_damage` / `hazard_direction` (see Spikes).
- **Audio**: `res://scripts/audio.gd` autoload `Audio`. `Audio.play(id, volume_db=0, variant=-1)` (one-shot, non-positional), `Audio.play_at(id, position, ...)` (positional, pooled `AudioStreamPlayer2D`s, `MAX_DISTANCE` 280px for the 4x zoom), `Audio.make_loop(id) -> LoopPlayer` (`add_child` it, `.start()`/`.stop_loop()`), `Audio.play_music(id, fade)`/`stop_music(fade)` (two-player crossfade). Ids are `StringName`s scanned from `res://audio/<folder>/<filename>`: lowercased, spaces→underscores, trailing digits stripped and treated as variant number (`player/jump1..5.wav` → id `player/jump` with 5 variants, pitch/volume jitter via `AudioStreamRandomizer`). **A sound whose name legitimately ends in a digit will be misread as a variant of a shorter id** — rename rather than fight it. `music/` ids are the plain filename, no variant handling. Unknown id: silent if listed in `Audio.PLANNED` (called for but no file yet), else one `push_warning`. **Standing rule: a new gameplay element isn't done until its sound hook exists.**

## Level editor seams (stretch goal)

A runtime level editor is a stretch goal with no plan to build it yet. The provisions below keep it possible, so every change from now on should respect them. The first is built (levels load through `Game.load_level()`, see Level loading); the next two are decided when a level can be edited at runtime; the rest are habits to follow whenever the code they concern is touched.

**Built: the loading entry point**
- **One loading entry point that takes a level source** plus a level id: `Game.load_level(id, source)` (a res:// path or a `PackedScene`; null = the catalog's path for the id). Respawn, `restart_level()`, next-level and the pause menu's pick all go through the id and source `Game` remembers, never `scene_file_path`, so a level need not be a file. Level identity is the id: the checkpoint is scoped to it, and `Game.level_root()` replaces `current_scene` wherever "the level" is meant. A custom source (a level assembled from data, a downloaded pack) needs only to produce a `PackedScene`, or a node tree wrapped in one, and an id; ids are permanent once levels are shared. Shared levels must never be `.tscn` files loaded from untrusted sources (a scene can reference scripts): the safe route is a data-only format that names built-in object types, positions and exports.

**Do when a runtime level editor is built**
- **A placed object's identity is its node name.** Snapshot keys are each saveable's path relative to the level root (`Game._key()`), and `PowerTarget.sources` is an `Array[Node]` of node references (stored as paths), so a runtime editor must give every placed object an explicit, unique, stable name (a duplicate added with a bare `add_child()` is auto-named), and renaming or moving an object drops its saved state. `Game.apply()` also frees every saveable with no snapshot entry, so any level edit must clear the checkpoint (`restart_level()` semantics), or a newly placed object would be freed on the next respawn. `PowerTarget.add_source()` works at runtime.
- **Runtime code never writes an export.** Authored values stay exports and anything the game mutates is a separate variable, as `WaterBasin` does (`initial_fill_depth_below_surface` authored, `fill_volume` runtime), so an in-place play-test can return to the untouched level. It is a preference rather than a hard requirement if a play-test always runs a fresh instance of the saved level, as the reload path already does. Audit status, open violations and the re-runnable scan are in `export-audit.md` and `audit_export_writes.py`: update the log whenever you audit or change an object, and fix a listed violation when the object is next touched.

**Habits**
- **Derive-from-level steps are named methods** called from `_ready()`, not inline: the basin's floor sampling, the conductor circuits (built once at load; painted tiles don't rewire today), the gem count, the checkpoint `order` (`_assign_order()` only runs under `Engine.is_editor_hint()`, so a checkpoint placed at runtime would get order 0). An editor can then re-run them after a change.
- **Authoring overlays** (the turret aim preview, wire links, see-saw gizmos) are gated on a flag, not on `Engine.is_editor_hint()`.
- **Configuration warnings are plain methods returning strings**, with `_get_configuration_warnings()` calling them, so a runtime level validator can reuse them.
- **Configuration lives in exports** (the existing pattern), so an inspector can be generated from the property list at runtime.
- **Level format stays `.tscn`.** `PackedScene.pack()` can save at runtime; placed nodes need `owner` set, and generated pieces (the conveyor's pieces, the conductor, finish and see-saw overlays) are all deliberately unowned, so they are never packed. A custom format is only worth it for sharing or hand-edited levels, and the single loading entry point keeps that open.

## Player (`player.gd`)

State is a single `enum State` + `match`, decided each frame from physics reality (`is_on_floor()`, `velocity.y` sign, input) rather than tracked as an independent flag — deliberately simple rather than a node-per-state architecture. One-shot animations (kick, uncrouch, mantle, climb-down, hurt) share one `enum OneShotAction`; held states (`is_crouching`, `is_climbing`, `is_hanging`) are separate bools with their own lifetimes, not folded into the enum.

- **Movement**: horizontal from `move_left`/`move_right` axis; gravity + jump with coyote time and jump buffering (independently counting-down floats, consumed together). `floor_snap_length` is raised to `slope_snap_length` (8px, not the 1px default) — walking down a slope moves horizontally first and can leave the floor several px below the body within one physics tick, which the 1px default can't snap across, causing `is_on_floor()` to flicker false and the player to visibly hop; snapping is skipped automatically while `velocity.y < 0`, so jumps are unaffected. Side effect: any step down smaller than the snap length is walked down rather than fallen off (no coyote window for those).
- **Slippery floors**: duck-typed like `get_conveyor_speed()` — `_floor_is_slippery()` does a short downward `test_move()` (not last frame's slide collisions: grounded, `velocity.y` is 0, so the slide often records no floor contact at all) and asks whatever it's standing on for `is_slippery() -> bool`. On a slippery floor the horizontal block builds toward `input_dir * speed` at `ice_accel` and decays toward 0 at `ice_friction` (also while crouching/kicking) instead of snapping. `_slide_vx` holds the player's *own* horizontal velocity, separate from `velocity.x`, because `velocity.x` also gets the conveyor and water pushes added each frame; every non-climb/hang/swim branch refreshes it (before the pushes), so stepping onto ice from normal ground carries momentum, capped at walk speed when re-entering the slide. It's zeroed on running into a wall and on entering the hurt/dead branch. Only `IceBlock` implements `is_slippery()` so far; the surf reads its own, separate contract for the same surfaces (`get_surf_friction_scale()`, see Surf).
- **Rising rigid floors**: `_lead_rising_rigid_floor(delta)` runs right after `move_and_slide()`. A `RigidBody2D` floor (an ice or metal block on a rising level) moves after the player's own step, so the engine's carry plus the floor snap would put the player back on the surface it just left and the block would rise into a rider that stayed put. When the player is on the floor, the platform velocity is rising faster than `RISING_FLOOR_MIN_SPEED` (1 px/s) and a 2 px downward `test_move()` finds a `RigidBody2D` rising at that speed, the player moves up by the floor's rise for the tick with `move_and_collide()` (stopping at a ceiling), so it sits where the surface will be. Other moving floors (platforms, belts, planks) are untouched. Standing on a floating block while the level rises needs no swim-state special case: the block keeps its rest fraction, so the swim probe never reaches the water.
- **Crouch**: a runtime-derived shorter `CollisionShape2D`, built once in `_ready()` from whatever shape type is present (`RectangleShape2D`: half height; `CapsuleShape2D`: half height clamped to two radii, since a capsule can't be shorter than its own caps — note Godot 4's `CapsuleShape2D.height` is the *full* height including caps, not the cylinder segment only). Standing back up is blocked by a real `intersect_shape` physics query, not `is_on_ceiling()`. **Any resource shared across scene instances (a `Shape2D` on a `CollisionShape2D`) must be `.duplicate()`d before being mutated at runtime**, or every instance of that scene fights over one shared resource — this bit both the player's crouch shape and the Crusher's resized arm shape.
- **Kick**: a one-shot action ending via `animation_finished`, gated against crouch. `KickHitbox.body_entered` has two independent duck-typed contracts: `take_damage(amount) -> int` (enemies, `Mirror`) and `kicked(direction: float)` (−1 left / +1 right, from `sprite.flip_h`; `IceBlock` uses it to know which way to slide). There is no dash and no dodge: the only immunity is the post-hit `hurt_invincibility_timer`. **Air kick**: a kick pressed while airborne (not crouching, climbing, hanging, swimming or surfing, and not the same press that mounted or dismounted the board) starts the same one-shot through `_start_air_kick()`, with the same animation, sound and hitbox. It differs from the ground kick in two ways: it does not root the player (`_air_kick` is true, so the KICKING branch of the horizontal movement is skipped, and a carried swing or dismount momentum survives it), and with `air_kick_halts_ascent` (default true) it sets `velocity.y = maxf(velocity.y, 0.0)`, cancelling the rise. It never slows a fall, so spamming it cannot hover. While the animation plays no ledge, catwalk or swing grab can start (they need `one_shot_action == NONE`). Landing mid-kick just lets the animation finish. Uses the ground kick art for now.
- **Climb (ladder)**: held state, not a `OneShotAction`. Ladder membership is **collider overlap**, sampled along the current collision shape's centerline (so it respects crouching) — not origin-cell membership — so a ladder whose top is flush with a floor stays grabbed until the feet actually clear it. Mounting from *above* (standing on a surface a ladder continues through) is a separate downward probe gated on down-input only. Landings (both directions, on any floor a ladder passes through) stop the player there rather than carrying them through; `climb_up_latched`/`climb_down_latched` stop a still-held key from instantly re-triggering a grab/crouch right after a landing. Vertical movement overrides gravity and locks horizontal, x-snapped to the ladder cell's center column.
- **Ledge hang + mantle**: grab detection runs every physics frame while airborne, on-wall, and descending (not collision-enter-only, so a jump alongside a wall can grab a ledge above the first contact point). Two raycast probes (forward clearance, headroom) gate the grab; a separate raycast pass finds the actual wall-face/ledge-top corner rather than trusting wherever `move_and_slide()` left the body. `_is_hangable_surface()` accepts tiles `SurfaceTypes.is_hangable()` approves (`"ground"`/`"glass"`/`"catwalk"`) or group membership (`"ground"` or `"catwalk"`); a body that also has `is_hangable()` (`MeltableBlock`, `RotatingBody`) is asked at the grab and every frame of the hang. Mantling up (`climb_up` pressed while hanging) tweens position to a computed target over half the `climb_up` animation's actual duration.
- **Catwalk underside hang + brachiate**: a second, parallel hang path (`hang_style: HangStyle` — `LEDGE` or `CATWALK_UNDER`) for grabbing a one-way catwalk's underside — no wall check at all, since a catwalk's one-way collision produces no side contact. Detection is a single straight-up raycast (raycasts are assumed to ignore `one_way_collision`, unlike body collision resolution). Reachable by an airborne jump that doesn't clear the catwalk, or by crouch+jump while standing on one (animated via a reversed `climb_up` clip). Once hanging in this style, holding left/right brachiates hand-over-hand along the underside (`catwalk_brachiate_speed`), playing the `"brachiate"` animation only on frames that actually displace the player and freezing it otherwise (including when blocked by the catwalk's end — travel is clamped there, not dropped). Pressing up/down while brachiating over a ladder cell hands off directly into the Climb state. Mantling up through a catwalk uses the same mantle machinery as a ledge mantle, but with its own `catwalk_mantle_offset` (x-symmetric — there's no wall corner to offset around). **Crust** (roadmap 6.1): a basin's crust body joins group `"crust"` (never `"catwalk"`, so lasers, water and steam still stop on it) and the same hang accepts its underside: the up-probe's `is_catwalk` key is also true for a crust hit (`_is_free_crust_hit()`), but only if `WaterBasin.is_underside_free(x, top, bottom)` says no liquid lies anywhere in the span the hanging body would fill, so it only works over a void left by a drain and is refused while liquid fills the space. Brachiating re-tests that at each candidate x (it stops where the crust ends or liquid begins), and a hang lets go if liquid rises into the body (`_hang_crust_blocked()`). A mantle up onto crust ends at the crust's own collision top (`_crust_mantle_target()`: the catwalk formula applied to `get_crust_collision_top_world_y()`), so the feet land on it with no drop. The crust's walkable collision starts `CRUST_COLLISION_TOP_INSET` (1 px) below its top face, because the art's first row is empty and a standing player looked to float; only the collision moves. A crust hang is anchored `crust_hang_lift` (3 px) higher than a catwalk's so the hands meet the crust's drawn underside; while hanging, the up-probe starts that much lower (a ray that starts inside the crust's collider never hits it, which stalled the brachiate). The crouch+jump entry from above (roadmap 6.2) works on crust too: the feet probe's `is_crust` key is true when the player stands on crust whose underside is free of liquid (`_crust_hang_is_free()`, the same test as the grab, on the standing collider), and `_try_climb_down_to_catwalk_hang()` then animates the reversed `climb_up` down to the same anchor the airborne grab uses (`WaterBasin.get_crust_underside_world_y_at()`, the crust's bottom or the seabed where that clips it). Over liquid it is refused and the ordinary crouch+jump fires; the catwalk entry is unchanged. Not hangable from the side: crust is not in `"ground"`.
  - **`hang_style` must be set explicitly by every function that starts a hang** (`_start_hang`, `_start_catwalk_hang`, `_begin_catwalk_climb_down`, `_start_swing_hang`) rather than relying on its default — it isn't reset automatically between hangs, so a stale value silently misdirects the mantle-offset branch on the *next* hang.
  - **`is_on_floor()` and `velocity` read stale while `is_hanging` is true**: a hang skips `move_and_slide()` entirely for its whole duration (needed so the pinned hang position never gets physics-resolved), so anything that reads those mid-hang is seeing whatever they were the instant before the hang started, not the current state.
- **Swing hang** (`hang_style` `SWING`; see the Swing bullet under World objects): a third hang on the same machinery (`is_hanging`, no `move_and_slide()`, state `HANG`, the `hang` animation, `hang_hand_local_offset` for the hand) with the hand pinned to a moving bar. `_try_grab_swing()` runs with the catwalk grab's gates (airborne for `hang_min_airborne_time`, no regrab lockout, not climbing/swimming, no one-shot) and no velocity condition, so a jump can catch the bar on the way up: the nearest swing in group `"swing"` whose grip is within its `grab_radius` of the player's hand point wins. `_start_swing_hang()` snaps the hand onto the bar, calls `attach_rider()`, hands the swing the velocity the player arrived with (`catch_momentum(velocity)`, read before it is zeroed; in the air that is the frame's `velocity` after `move_and_slide()`, so horizontal momentum is whatever the air control or a carried `_air_carry_vx` set) and keeps the facing fixed for the whole hang. The pin is done by the swing (`pin_to_swing(anchor)`, called from `Swing._physics_process()` right after it moves), not by `_follow_hang_platform()` (`hang_platform` stays null). While hanging, `_update_swing_hang()` passes left/right to `Swing.set_push()` every frame; `crouch` drops, `jump` jumps, `climb_up` does nothing. `_release_swing(jump)` sets `velocity` to `Swing.get_velocity_at(global_position)` (tangential velocity of the body about the pivot), adds `jump_velocity * swing_jump_boost` (default 1) to `velocity.y` on a jump, clears `jump_buffer_timer` and sets the regrab lockout. **Momentum carry**: the ordinary horizontal block overwrites `velocity.x` with input every frame, so after a release `_air_carry_active` makes it use `_air_carry_vx` instead: untouched with no input; input steers toward `input * speed` at `carry_air_accel` (400 px/s²), except that pushing the way you are already going above walk speed never slows you. It ends on the floor, a ladder, swimming, a hang, any one-shot action, or `_interrupt_current_action()`, and a wall contact (checked right after `move_and_slide()`) zeroes it when it points into the wall. `_slide_vx` follows it, so landing on ice keeps the momentum (capped at walk speed). `_interrupt_current_action()` and `_force_release_hang()` detach from the swing.
- **Surf** (`is_surfing`, `State.SURF`; its deferred polish is under Roadmap: before level design and level loading, its standing risks under Surf risks): a held state that owns the crouch collider (`wants_crouch` includes `is_surfing`, so it is kept in the air too; up/down are zeroed so ladders and the ladder mount are suppressed). **Mount**: kick while crouching on the floor (`_start_surf()`, before the ordinary kick block); **dismount**: kick again (`_end_surf(true)`: on the ground the player stops and the crouch logic stands up; in the air the speed goes to a steering air carry and the player stands at once via `_stand_up_instantly()`, because the UNCROUCHING one-shot would cancel the carry). Facing is locked at mounting.
  - **Ground speed**: its own `_surf_speed` along the travel direction (not `_slide_vx`), starting at `surf_start_speed` (240), changing each step by `gravity * t.y * surf_slope_gain` (1.25; t is the floor tangent in the travel direction, `t.y` < 0 uphill, so downhill gains and uphill loses fast) minus the friction (`surf_friction` 320 dry, about 5 tiles of coasting on the flat from the start speed, eased toward `surf_friction_wet` 80 by the wetness, see Water, then multiplied by the floor's friction scale, see Surface friction) minus the tilt-mismatch drag (and `surf_skim_drag` while skimming), clamped to 0..the top speed (`surf_top_speed` 600 dry, eased toward `surf_top_speed_wet` 800 by the wetness). It ends below `surf_min_speed` (40); a wall zeroes it, so a wall ends the surf the same way. The velocity is `t * _surf_speed` minus `SURF_FLOOR_PRESS` (60 px/s) along the floor normal: a velocity exactly along an uphill slope never touches it, so `is_on_floor()` flickered false (and the floor snap is off while moving up) without the press. Floor normals within `SURF_FLAT_NORMAL_X` (about 3°) of up are treated as exactly flat (contact normals are noisy, and a tiny upward tangent also cancelled the snap). The press is not part of `_surf_prev_velocity`, which stores the pure tangent velocity a launch or landing should read. Because `_surf_speed` is kept across floor changes, joints between slopes and flat lose no speed; only air landings cost (below). The conveyor and water pushes still add on top of `velocity.x` and don't change `_surf_speed` (the water push is multiplied by `surf_water_push_scale` while surfing; for the belt, see Conveyors, jump pads and the swing below).
  - **Tilt** (left/right, relative to the facing; up/down unused): input toward the travel direction is nose down, against it is nose up, none is level (`_surf_tilt_sign`: +1 up, -1 down, 0 level; deadzone 0.3). Match is by sign: ground sign is +1 uphill, -1 downhill, 0 flat (floor angle under `surf_flat_threshold_degrees`, 8°). A matching tilt costs nothing; a level board on a slope adds `surf_drag_level` (150); any other mismatch adds `surf_drag_wrong` (400), including nose up/down on the flat, so pulling the nose up on the flat is a hard brake (about 35px of coasting against about 82). The drawn board eases (`surf_tilt_ease_degrees_per_second`, 720) to `surf_tilt_down_degrees` (26.57, 2:1) or `surf_tilt_up_degrees` (45, 1:1) by rotating the `SurfBoard` node (`rotation = -angle * facing`); that is looks only, the match uses the target at once.
  - **Leaving the ground** (a ledge, a ramp lip or a jump): `_surf_move()` detects it on the first airborne frame (or the jump consumed by `_surf_jump_pending`), takes `_surf_prev_velocity`, rotates it by the tilt (`_surf_launch_bias()`: nose up `surf_launch_pop_degrees` 12° upward, nose down `surf_launch_dive_degrees` 10° downward, magnitude kept; skipped for a coyote jump already in the air), adds `jump_velocity * surf_jump_boost` to the vertical part on a jump (so a slope's vertical tangent is kept), and hands it to the shared air carry with steering off. A ramp lip needs no code: the upward tangent suppresses the floor snap, so the board simply leaves. Checked: a 1:1 ramp launches along 45°, nose up launches higher and shorter, nose down flatter. A 1:1 slope costs about 1,100 px/s² of speed uphill, so a ramp 2.5 tiles high needs roughly 500 px/s to launch, a 1-tile ramp about 320; downhill 1:1 matched reaches the 600 cap quickly.
  - **Landing** (carry active and the floor reached): `_surf_landing_speed()` takes the arrival velocity (`_surf_prev_velocity`) along the new floor's tangent (what is into the floor is lost), multiplied by `surf_landing_level` (0.85) for a level board on a slope or `surf_landing_wrong` (0.5) for any other tilt/ground sign mismatch, capped at the current top speed (the wet one when the floor reached is wet); a clean landing on a matching slope keeps it all. Checked: the same ramp jump landing on the flat keeps about twice the speed level as with the nose still up.
  - **Bowling** (stage 3): from `surf_bowl_speed` (300 px/s: the ground speed, or the horizontal carried speed in the air; `get_surf_speed()` is the public getter, 0 when not surfing) `_surf_bowl_sweep()` runs each physics frame just before `move_and_slide()`. It is a swept shape query, not a `KickHitbox`-style `Area2D`: a rectangle covering this frame's motion (start and end boxes, so slopes and jumps are covered) plus `SURF_BOWL_LEAD` (8 px) ahead on layer 1 (actors), calling the optional `bowled_over(direction, surf_speed) -> bool` on each body that has it, `direction` being the locked facing. An Area's overlap would only be seen a step late, after the player had already stopped against a solid target. A body that returns true gets `add_collision_exception_with()` on the player at once, because a bowled body only disables its own shape with `set_deferred()` (or `queue_free()`), which is too late to stop this frame's move; the exception is left behind, which is harmless (stale RIDs). The surf keeps all its speed after a bowl. A body without the method, or one that returns false, is left alone and stays solid, so the surf stops against it (a wall). Checked: a fast surfer bowls a grunt and keeps going; below the threshold the grunt stops the surf; a non-opt-in solid body stops it even when fast; a Drillbot facing the way the surfer travels is bowled and one facing the surfer is not; a motionless grunt floating at jump height is bowled in the air. The same query serves every `bowled_over()` implementer (grunt, Drillbot, the breakable barrier). Sound `player/surf_bowl` is in `Audio.PLANNED`.
  - **Shoving blocks** (the surf as a long-range kick): the same sweep also reads a second optional contract, `surf_shoved(direction, surf_speed) -> float`, from bodies with no (or a false) `bowled_over()`; `MeltableBlock` implements it (see its bullet). A negative return refuses and the body stays solid, so the surf stops against it. Otherwise the return is the surf speed the shove cost, taken off `_surf_speed` (or the carried air speed) from the next frame, and the player takes a collision exception with the block and tracks it in `_surf_shoved_bodies` (instance id → body, `touched`, `age`): the block is solid and can't leave in one frame, so the surfer passes through it, and `_update_surf_shove_exceptions(delta)` (top of `_physics_process()`, every state) drops the exception only after the player's collider, grown by 1 px, has overlapped the block and then stopped (`intersect_shape()` ignores exceptions, so it sees the overlap they hide), or after `SURF_SHOVE_GIVE_UP` (0.6 s) without ever touching it. The exception is taken while the block is still up to a frame's motion plus `SURF_BOWL_LEAD` ahead of the board, so it must not be released on "not overlapping" alone: a released body is shoved and charged again, every frame of the approach. A body still in the list is skipped by the sweep. Only a block in front counts: `_surf_shove_reaches()` repeats the query with the player's own height, the bottom 3 px trimmed and no vertical motion, so a block the board stands on or lands on is a floor and is never shoved.
  - **Surface friction**: the floor under the board scales the ground friction (after the wet blend; slope gain, the mismatch drag and the top speed are untouched), so a material changes the coast distance without touching anything else. `_surf_floor_friction_scale()` finds the floor with a short downward `test_move()` (a normal within 60° of up) and reads it from either of two optional sources, 1 if neither says anything, clamped to 0.05..10: a body's duck-typed `get_surf_friction_scale() -> float` (below 1 coasts further, above 1 stops sooner), or a tile of the world tilemap whose TileSet has a float custom-data layer named `surf_friction` (0 or unset = 1; the layer is on the glass tile in `ground_tileset.tres`, set per tile in the TileSet editor; a missing layer is skipped). `IceBlock` implements the method with its `surf_friction_scale` export (0.25: about four times the dry coasting distance, 80 px/s² against 320, so about 22 tiles against 5.6 from the start speed). A new material (mud, gravel) is a body with the same one method, or a tile value above 1; a basin's skim floor has no method, so a skim uses the plain wet friction. The scale applies on top of wetness, so a wet ice block is slicker still and wet mud still drags.
  - **Water** (stage 4; soft gate: dry ground works, water is better). Three surfaces. *Dry ground*: the values above. *Running film* (flowing particles over the floor: streams, runoff, a melted ice block's water): `_update_surf_wetness()` reads `WaterManager.get_floor_wetness(feet, half_width)` while the board is on the floor, a 0..1 coverage of the footprint by non-hazardous particles in a thin band above the feet that are running (above `WET_MIN_SPEED`, not falling or bouncing, so a waterfall overhead or settled liquid doesn't count; slag is a hazard, not a surface, and counts nothing). `_surf_wetness` rises at once and falls linearly over `surf_wet_decay_time` (0.4 s), so the noisy reading can't flicker the friction; it decays in the air too, so a short hop keeps it. The ground friction eases from `surf_friction` to `surf_friction_wet` and the top speed from `surf_top_speed` to `surf_top_speed_wet` by it, so leaving a stream eases the speed back to the dry cap rather than cutting it; the flow's own push (`get_player_push()`, added to `velocity.x` as always) is scaled by `surf_water_push_scale`, so with the current is faster and against it slower. *Settled basin* (skim): at or above `surf_skim_min_speed` (180), `_update_skim_floor()` (called each frame just before `move_and_slide()`) asks `WaterManager.find_skim_basin()` for the basin under the board (liquid over that column that is not hazardous right now, so not slag and not water a spark has electrified, no crust, surface at or below the feet or up to `SKIM_CATCH_DEPTH` 6 px above them, feet not below the seabed; with basins stacked in a column the nearest surface below wins) and raises that basin's skim floor (`WaterBasin.set_skim_floor()`): a thin one-way `StaticBody2D` on layer 3 laid flat on the flat liquid line across the interior columns (plus 2 px into the walls), its one-way margin set to the catch depth. Because it is a real floor, landing, riding, flat-floor tilt matching (level is the match), jumping and launching off the surface all use the ordinary surf code with no special case, and the swim state never starts while it holds (the swim probe stays above the surface). On the surface the floor reads fully wet (`_surf_on_skim`) and `surf_skim_drag` (160) adds to the friction, so a skim is short without speed. The floor is re-placed on the current liquid line every frame it is up and dropped when the surf ends, the player leaves the basin's columns, or the basin changes. Below the minimum speed no floor is raised and the player falls into the ordinary swim (`_update_swim_state()` ends the surf); a surfer riding the surface that drops below it ends the surf, stops and sinks the same way. A dismount on the surface also sinks. Slag is never skimmed, and neither is electrified water while it lasts (no floor is raised; the hazard and swim entry apply), a crusted basin is just solid ground, and particle water is not skimmable. Cosmetic only: a splash and `player/surf_splash` on first touching the surface (`SWIM_SPLASH_IMPULSE` times the arrival vertical speed) and a wake behind the board each frame (`SKIM_WAKE_IMPULSE` times the speed) through `WaterBasin.disturb()`; nothing touches fill volume. A basin's far wall is an ordinary wall: below the rim it ends the surf, at the rim (a full basin) the surface continues straight onto the wall top. The water chain for level design: melted ice runs down a slope and makes a wet route, a skim crosses a pool, a crusted slag lake is just a floor, and a basin's rim or sloped floor tiles are natural ramps. The player's mask includes layer 3 (added in `_ready()`). **Steam lift**: only while surfing, `_surf_move()` smooths `WaterManager.get_steam_lift()` (see the Liquid system) over the collider's rect into `_surf_steam_lift` (0..1; passing its previous value and the frame time, so the manager does the smoothing, and 0 whenever the surf isn't running). In the air, `_apply_surf_steam_lift()` accelerates the board upward by `surf_steam_lift` (1500 px/s², on top of gravity, so full steam nets 600 up) times the lift, never beyond `surf_steam_max_rise` (120 px/s) and never slowing a faster upward speed (a jump pad's). On the floor, once `surf_steam_lift` × the lift exceeds `gravity` (900) the board leaves it: that frame departs like a ramp lip, without the tilt's launch bias and keeping only the upward part of the floor-tangent velocity (downhill it would point into the floor and the snap would hold the board down), and the ground branch is skipped until it lands again. Below that threshold steam does nothing on the floor. Lift only writes the velocity, so a solid ceiling still stops the board; the walking player, a swimmer and blocks never read steam. The two exports and the decay time in the manager are placeholders to tune against the column's height and density. A reading doesn't cut out the instant a surfer leaves the column: it decays over `STEAM_LIFT_DECAY_TIME`, so the board keeps rising briefly past the column's top.
  - **Conveyors, jump pads and the swing**: *Conveyors*: a belt is a moving floor. `_surf_move()` reads `_conveyor_push_speed()` into `_surf_belt_vx` each grounded frame (0 in the air, off belts and when the surf starts or ends); friction, slope gain, tilt drag and the top speed stay relative to the board's own `_surf_speed`, the shared conveyor line in `_physics_process()` adds the belt to `velocity.x`, and the speed over the ground along the travel direction is `_surf_speed + _surf_belt_vx * facing`. `get_surf_speed()` returns that on the ground (so the bowl threshold and the speed trap read the true ground speed; in the air it is the carried horizontal speed as before), `_surf_prev_velocity` includes the belt so a launch off a belt's end carries it (the landing doesn't subtract it again, so a belt gives a small net boost), and the **stall gate** ends the surf (stop, stand up) when that ground speed falls below `surf_min_speed`: a belt as fast as the board against it stalls it at once, a slower one only slows the ground speed. *Jump pads*: `launch()` doesn't tear anything down while surfing; it buffers the vector with `_pending_launch_keeps_surf` and `_apply_surf_launch()` (last in `_physics_process()`, like every launch) replaces the vertical velocity with the pad's and adds the pad's horizontal part to the board's horizontal velocity (`_air_carry_vx` if already carrying, else `velocity.x`), hands the result to the shared non-steering air carry and `_surf_prev_velocity`, and applies no tilt bias, so the board leaves the pad with the speed it had, lands back into the surf and keeps the speed (a straight-up pad at 445 px/s took off at 445 and landed at 445); if the surf ended before the buffered launch is applied it falls back to a plain velocity write. A non-surfing player is launched as before, through `_interrupt_current_action()`. *Swing*: the swing grab gate has no surf exclusion, so a surfing player in the air grabs a bar like any other airborne player: `_start_swing_hang()` reads the surf velocity into `catch_momentum()` before `_end_surf(false)`, the board vanishes and the swing takes the whole speed (400 px/s on the 64px default rod is about 6.2 rad/s). A swing with angle limits (±80° in `swing.tscn`) pins at the limit and zeroes the angular velocity there, so a fast catch swings to the stop and back; a swing meant to take a big arc or a loop needs `free_rotation` (it then swung past 100° in the check), and `catch_transfer` tunes the share.
  - **Drop platforms and the see-saw** (no surf code): a drop platform's countdown latches and can't be cancelled, so a fast surf across a long one beats it. A level see-saw plank is crossed at speed with no loss beyond the ordinary friction; a tilted plank is a ramp when approached from its low end, but its raised end is a lip of about `half length × sin(angle)` px that stops a fast surf like a wall, so a see-saw on a surf route needs the surf to arrive on the low side (or a plank end that sits flush at its extremes).
  - **Ends without keeping momentum** (all via `_end_surf(false)`): `_interrupt_current_action()` (a hit, a dance; a jump pad launch doesn't come through here while surfing), grabbing a swing (`catch_momentum()` is given the surf velocity first), and entering water with no skim floor up (too slow, or slag; see Water). Ledge and catwalk grabs and the catwalk climb-down are gated off while surfing.
  - **Shared air carry**: the swing's carry was generalized: `_air_carry_active/_vx/_steers`, `_begin_air_carry(vx, steers)`, `carry_air_accel`; steering carries (swing release, dismount) let left/right steer toward `input * speed`, non-steering ones (surf) don't; it ends on the floor, a grab, a one-shot, an interrupt, and a wall contact zeroes it.
  - **Board and audio**: a separate `SurfBoard` `Node2D` in `player.tscn` (script `surf_board.gd`, class `SurfBoardArt`, placeholder drawn in code facing right, origin on the board's top surface) placed under the feet each frame and mirrored by `scale.x`, hidden unless surfing; the `fall` animation is the placeholder pose. `player/surf_start`, a `player/surf_loop` loop (off in the air and while skimming, pitch follows speed), a `player/surf_water_loop` loop (only while skimming, same pitch) and `player/surf_splash` (touching a basin's surface, positional) and a `player/surf_steam_loop` loop (volume follows the steam lift, silent without it) are in `Audio.PLANNED`. `get_surf_speed()` is the public speed getter (the bowl threshold and the speed trap read it).
- **Swim**: held state (`is_swimming`, own lifetime, same convention as `is_climbing`/`is_hanging`), entered/exited via a hysteresis on `_water_surface_depth()` — a per-column depth query against whatever `WaterBasin` the player's column belongs to (via `water_manager`), not tile membership or an `Area2D` overlap (`swim_enter_depth`/`swim_exit_depth`; `swim_probe_offset_y` raises the probe point to roughly chest height so entry/exit read right rather than triggering at the collider's center). Vertical input reuses `climb_up`/`crouch` (with `jump` folded in as an extra up-source) and drives `velocity.y` directly (`swim_up_speed` up, `swim_speed` down/horizontal); with nothing held, `velocity.y` eases toward a slow passive-sink target (`swim_sink_speed`) via `move_toward()` at `swim_gravity`'s rate, and is hard-capped to `swim_speed` the instant swimming starts so a body that fell before reaching the water doesn't carry an unbounded velocity into it. `_set_swim_collider()` rotates the collider 90° for the horizontal swim pose, anchoring whichever wall edge is currently touched across the rotation so it doesn't leave a gap or shove the player away from the wall. The rotation is refused if the rotated collider would overlap a solid at the player's position (`_swim_pose_fits()`, a real shape query) — a gap narrower than the swim pose between two ice blocks or a block and a basin wall — since the wide pose would pin the player between both sides with no way to move or leave swim state. In that case swimming carries on with the upright collider (`_swim_rotated` false while `is_swimming` is true) and `_update_swim_state()` retries every frame until the pose fits; un-rotating a pose that was never taken is a no-op. Consequence: the swim pose can also be refused beside a catwalk tile (the shape query doesn't honour one-way collision), which only leaves the player upright until they're clear of it. Kick, crouch-entry, ledge-grab, and catwalk-grab are all gated off while swimming; the water system's ambient particle push (see World objects below) is gated off too, since a swimming player owns their own velocity directly. A basin the player swims in can be hazardous right now (`WaterBasin.is_hazardous_now()`: slag, or water a spark has electrified), and then every frame of submersion calls `take_hit()` (`SLAG_CONTACT_DAMAGE` for slag, `ELECTRIC_CONTACT_DAMAGE` for electrified water; only slag floats you up, since only slag has a `swim_float_speed`). Slag is swimmable too, but strongly buoyant: with no vertical input, `velocity.y` eases toward upward `LiquidProfile.swim_float_speed` (60 px/s for slag, 0 = none, water keeps `swim_sink_speed`) via `_swim_passive_target()`, so the player drifts up toward an escape (swim-up 80 beats it, swim-down 120 still beats it), while `take_hit()` is called each frame of submersion, paced by its i-frames. The slag damage check runs in every held state too (hanging from a ledge or on a ladder with the probe point below a slag surface still hurts, and the hit knocks the player off); only swim entry/exit is gated on climbing/hanging. A hit drops swim state through `_interrupt_current_action()` and normal entry resumes once the hurt animation ends. While hurt or dead inside a buoyant liquid, `_process_incapacitated()` floats toward the same speed instead of applying gravity. Surfacing has no special "climb out" handling — crossing back above the exit threshold just hands off to whatever the next frame's normal floor/fall logic decides. See `water-mechanic.md` for the full constant list.
- **Health / Hurt / Dead**: `max_health` is 4 (the health bar art has 4 segments). `take_hit(damage, from_position) -> bool` is the damage contract (duck-typed via `has_method`), separate from the enemy-facing `take_damage(amount) -> int`. Knockback direction is which side of the hazard the player is on. HURT is a `OneShotAction`; DEAD is a terminal bool holding the last frame. Hurt/dead/dance all route through one early-return branch in `_physics_process` (gravity + friction-decay + `move_and_slide()` only) rather than being threaded through the normal per-state logic, since most of that logic doesn't itself check for incapacitation. On death `_schedule_respawn()` starts a tween bound to the player that calls `Game.respawn()` after the `dead` animation's length (summed from the SpriteFrames frame durations and speed) plus `respawn_delay` (3s, exported); a tween rather than `await` so it dies quietly with the player if `R` reloads first. `respawn_at(pos)` is the hard teleport `Game` calls after a restore: position, zero velocity, full health, `health_changed`, both interpolation resets. Only `take_hit()` kills the player — there is no kill plane. `_physics_process` returns right after `_update_swim_state()` when `is_dead` (slag's `take_hit()` runs inside it), so the state decision can't overwrite the `dead` animation with fall/idle.
- **Gems / win**: `collect_gem()` increments `gems_collected` and emits `gem_collected(count, total)`; `gems_total` is the number of nodes in group `"gem"`, counted once at load (deferred from `_ready()` so every gem has joined; gems free themselves on pickup, so never recount; a checkpoint restore sets both numbers from the snapshot and `_count_gems()` then does nothing, so the total stays the level's original one). `gem_collected(count, total)` is emitted on every pickup, and `gems_counted(total)` once when the load-time count is made (not when a restore supplied the total); `GemDisplay` and `Finish` listen. Collecting never wins by itself: the level's `Finish` calls `dance_through(center_x, slide_time, shrink_time)`, which runs the public `start_dance()` (terminal `is_dancing` flag, like `is_dead`; plays `player/win`, emits `won`) and returns a physics-process `Tween` that slides the body's x to the door centre and then shrinks the **sprite node's** `scale` to `DANCE_SHRINK_TO` (0.02, not 0) and hides it. The sprite is centred with no offset, so the node origin is the art's centre and it shrinks toward its middle, feet leaving the floor; collider, camera and kick hitbox are untouched. Don't change `sprite.scale`/`sprite.position` elsewhere. Dance is **not** gated through `OneShotAction`/`animation_finished` the way Hurt/Dead are — it's a one-way flag, so its animation is free to loop.
- **Jump pads**: `launch(vector: Vector2)` is the duck-typed contract a jump pad calls (mirrors `take_hit()`/`collect_gem()`). It drops out of any held state via `_interrupt_current_action()` (except the surf, which keeps going: see the surf's Conveyors, jump pads and the swing bullet), then buffers the vector rather than writing `velocity` directly — a pad's `Area2D` signal can fire at an unpredictable point in the physics step relative to the player's own `_physics_process` for that frame, and a direct write can land before either the grounded `velocity.y = 0` gravity reset or the unconditional `velocity.x = input_dir * speed` line has run, which would silently cancel it. The buffered vector is applied once, after everything else that touches `velocity` that frame, so it always wins regardless of ordering; the normal per-frame decide-state logic then turns the resulting `velocity.y < 0` into `State.JUMP` on its own, the same as jumping off a ledge-hang. **Any future code that writes to `velocity` must stay above that point in `_physics_process`, not below it**, or it'll have the same problem this fixed.
- **`_interrupt_current_action()`** is the single place that tears down whatever the player was mid-way through on a landed hit (kills the mantle tween, clears climbing, drops a hang with a re-grab lockout, stands up from a crouch if possible, resets the one-shot action, zeroes jump buffer/coyote timers). **Any new held state, one-shot action, or tween must be added here too**, or a hit mid-action leaves it dangling.
- **Facing**: `sprite.flip_h` plus `_update_kick_hitbox_facing()` (mirrors `KickHitbox`'s position around local x=0) fire together everywhere facing changes. `flip_h` mirrors strictly around the sprite node's own local origin and ignores `offset` — an off-center sprite (art with asymmetric canvas, e.g. the drillbot's drill) needs its `offset.x` manually negated to compensate, or mirrored around the sprite's own center instead by negating `scale.x`. An asymmetric `ConvexPolygonShape2D` collider needs its own points negated per-axis, not just its position.
- **Hard teleports** (hang grab, mantle snap, ladder mount) call `reset_physics_interpolation()` on **both** the player and the camera — a child node's own interpolation state doesn't get reset by its parent's, so skipping the camera produces a one-frame "world jumps toward the player and snaps back" glitch even though the player's own position is correct.
- **A tile-boundary rounding gotcha**: mapping a raw collision contact point to a tile cell with `local_to_map()` can round a boundary-exact point into the wrong (adjacent) cell depending on which side was hit. Nudge the point a half-pixel inward along the collision normal before mapping.
- **A non-looping one-shot `AnimatedSprite2D` animation left with Loop ON never fires `animation_finished`**, silently soft-locking whatever state depends on it — check Loop is off for every one-shot animation (`hurt`, `dead`, etc; `_ready()` warns if it isn't for the ones that matter).

## World objects

- **Moving platform** (`moving_platform.gd`): `AnimatableBody2D` + a looping `Tween` on `position` (`TWEEN_PROCESS_PHYSICS`, `sync_to_physics = true`). Riding needs **no player code at all** — `CharacterBody2D.move_and_slide()` already inherits a floor body's velocity, as long as the platform's motion happens inside the physics step (hence the physics-process tween). Hanging on a moving platform works by shifting the hang's pinned world-space points (`hang_anchor`, `mantle_target`) by the platform's per-frame position delta; the mantle tween accordingly uses `tween_method`/lerp between two world points rather than `tween_property` to a fixed target, since a fixed target can't be shifted mid-tween. A one-way platform that should also be ledge-grabbable needs thin one-way end-cap `CollisionShape2D`s (one-way direction facing sideways) at its outer edges — a plain one-way top shape produces no side contact for the grab to latch onto, and a solid cap would block jump-through at the ends.
- **Drop platform** (`drop_platform.gd`): a generous `Area2D` sensor (covers both standing-on-top and hanging-at-the-edge) latches a countdown once a player is detected on/hanging from it; committed once triggered (leaving early doesn't cancel). On drop, collision is disabled (deferred) and a hang from this platform is force-released. Reappears via a `VisibleOnScreenNotifier2D` made `top_level` so it stays pinned to the platform's original spot even after the body has fallen away.
- **Sawwheel / Crusher hazards**: poll `get_overlapping_bodies()` every physics frame and call `take_hit()` on anything that has it, rather than a one-shot `body_entered` — a hit can be ignored (i-frames/grace) while the hazard itself never moves, so a one-shot signal could mean the player is never re-hurt after immunity ends. Crusher derives its animation frame and hitbox position from one shared phase value each frame (extend/retract/dwell durations authored per-instance) rather than running the sprite and the collision as two independent clocks; its solid arm is a separate `AnimatableBody2D` sized off the same phase value the sprite and hitbox use, so all three can't drift out of sync. The crusher's danger hitbox also calls `shatter()` on anything it overlaps that has it (`MeltableBlock`), but only when the spike comes down on it (`_crushing_from_above()`): the crusher isn't on its retracting leg, and a point 1 px inside the bottom edge of the spike, on its centre line, is inside the block's collider (a physics point query on layer 1, where blocks sit). Ice then bursts into water as a melt does; metal is untouched. A block kicked into the side of the arm, or launched up into a rising spike, is merely stopped: a block pressed against the arm has its near edge at the arm's side, so the centre-line point stays outside it. **Jam**: a block whose `jams_crusher()` is true (`MetalBlock`, unless melted; false in the base class and for ice) stalls the piston. The arm extends as normal and `_latch_jam()` fires the moment the spike touches the block from above, using the same `_crushing_from_above()` test as ice (the crusher isn't retracting and the spike's centre-line tip point is inside the block's collider), polled in the same overlap loop. That covers metal already under the arm when the extend leg starts and metal that slides in mid-stroke alike, and the arm is drawn touching the block before it starts back. The latch sets `_jammed`, plays `traps/crusher_jam` once, parks the cycle clock at the start of the retracted dwell and freezes it; the arm then reverses at once to the park position at its retract speed (from `_retracted_fraction`, last frame's pose) and stays there, the spike harmless. A block pressed against the side of the arm doesn't touch the spike from above and doesn't jam it. - **Conveyor belt** (`conveyor_belt.gd`): a plain `StaticBody2D` on physics layer 2. `@tool`, so it builds itself: assign `left_cap_frames`/`mid_frames`/`right_cap_frames` (its three pieces of source art, each with `"left"`/`"right"` animations for the two travel directions) once per belt, and the exported `segments` count then drives everything, live in the editor. `segments` is signed and means total tile width, not mid-tile count: `0` clears the belt entirely (`Pieces` empty, collision disabled); `1` places a single mid tile with no end caps; `abs(segments) >= 2` places end caps at both ends with `abs(segments) - 2` mid tiles between. The sign controls which side of the node's origin the belt extends to — positive builds rightward from `x=0` (origin at the belt's left edge), negative builds the same layout leftward (origin at the belt's right edge) — so two belts can be placed origin-to-origin and extend away from each other, or a belt's origin can sit at whichever edge is more convenient for level layout. `_rebuild()` regenerates `Pieces` and resizes/repositions `CollisionShape2D`'s `RectangleShape2D` (or disables it, at `segments == 0`) to match; a shared `_segment_layout()` helper (returns tile count + build direction) is used by both `_rebuild()` and the debug draw below so they can't disagree. Rebuilding replaces whatever's currently under `Pieces` (the old children are removed from the tree at once so the new ones keep their names), so it isn't hand-edited directly; the pieces are given no `owner`, so they are never saved into a belt or level scene (a belt still being dragged in isn't under the edited root yet, and setting an owner then raises "Invalid owner"). Duck-typed like `take_hit()`/`collect_gem()`: the belt exposes `get_conveyor_speed()`, and the player's `_conveyor_push_speed()` reads that off whatever it's resting on each physics frame (via `get_slide_collision_count()`, filtered to roughly floor-facing normals) and adds the result straight onto `velocity.x` before `move_and_slide()` — a plain addition, so moving with/against a belt just adds two numbers rather than overriding either. `MeltableBlock` reads the same contract from its own previous-move slide collisions, but adds the belt speed only around its `move_and_slide()` and removes it again afterwards (its `velocity.x` is its own kick motion, which must neither inherit the belt nor fight it through slide friction). One frame of lag (the collisions read are the previous frame's) is inherent and not noticeable. Deliberately **not** added to the `"ground"`/`"catwalk"` groups and not part of `world_tilemap` — `_surface_type_at()` only recognizes those, so the ledge-grab system can never latch onto a conveyor, rounded end caps included, with no special-casing needed. The animation's `speed_scale` is derived from `belt_speed / REFERENCE_SPEED` (a hardcoded constant, measured once against the actual art at 10 px/s) rather than the SpriteFrames' own FPS, so belt speed and visual pace can never drift apart and a runtime speed change (`set_belt_speed()`, for a future speed-control button) automatically retunes the animation too. `enabled`/`set_enabled()` pauses the animation mid-frame (rather than hiding it) and zeroes the push, and is what `set_powered()` calls (powered = running). `debug_draw_bounds` (default on, per-instance, mirrors `player.gd`'s `debug_draw_hang_probes`) outlines the belt's actual built width/direction, ticks each tile boundary, and draws a small travel-direction arrow directly in the editor viewport via `_draw()`, redrawn continuously while `Engine.is_editor_hint()` is true (`set_process(false)` outside the editor, so it costs nothing at runtime) — useful for placing/sizing a belt before its art is assigned. **Editor-only pitfall, still live**: after placing a new conveyor instance in a level scene (or toggling Editable Children on an existing one), its `@tool` script can go on running stale — sprites not rebuilding, debug draw not appearing — until that level scene's tab is closed and reopened; the editor doesn't reliably refresh a nested instance's live tool-script state on its own. If a belt in a level looks wrong or its debug outline is missing, reopen that scene before assuming the script itself is broken.

  - **States** (`enum State`, decided each physics frame from the world; `_elapsed`/`_duration` time the current one): `PAUSE` (still, hammer upright, random time in `pause_time_min..max`; on ending it rolls `turn_chance` to turn round, then walks), `WALK` (`wander_speed`, random time in `walk_time_min..max`; a wall in its heading or a ledge ahead turns it round into a PAUSE whose end does not roll the random turn), `CHASE` (`chase_speed`, faces the player each frame; at a ledge it stands still instead of walking off, at a wall the move stops it; there is no turning and no pathing), `WINDUP` (`windup_time`, facing locked, the telegraph), `SWING` (`swing_time`, the only live state), `RECOVER` (`recover_time`, hammer down and inert, the grunt open). The wall test is `is_on_wall()` with the wall normal opposing the heading, after the move, so slopes within the floor angle are not walls.
  - **Hammer**: a separate `Area2D` (`HammerPivot/Hammer`, layer 0, mask 1, monitoring off) under a `HammerPivot` `Node2D` at the shoulder (0, -4); it only holds the hitbox, a 4×16 rectangle starting at the pivot. Hits come from `_sweep_hammer()`, **not** from the Area's overlaps: an overlap is a physics step stale, and the swing eases in so most of its angle is covered in its last frames, so polling the Area never saw the hammer past about 40° (only a player pressed against the grunt was hit, and a crouching or surfing one ducked it). Buoyancy helpers: `_submerged_fraction(liquid_type)` (the area of the block's rotated rectangle below the settled liquid surface of the basin at its centre column, a polygon clip, via `WaterManager.get_basin_for_column()` and `get_liquid_surface_world_y()` so crust doesn't count; it also records the submerged area's centroid, the centre of buoyancy) and `_buoyant_accel(submerged, riders, liquid_type)`, `GRAVITY * (1 - submerged / rest_fraction)` (plus, with rotation allowed, the couple between the centre of buoyancy and the centre of mass as angular acceleration) where `rest_fraction = float_depth_fraction + riders * rider_load_tiles / block area` — zero net force at the rest fraction, upward when deeper, and `rest_fraction >= 1.0` can't carry the load and sinks (the carrying-capacity lever for level design). Riders: `_actors_in_band()` (a thin `intersect_shape` band across the top face of the block taken as an upright rectangle, width and height swapped on its side, counting layer-1-only bodies, never a player hanging from this block) is applied the instant a rider is detected, so behaviour doesn't depend on the block having settled. **Rising and draining levels:** a floating block rides the surface. `_damp_vertical_in_liquid(coefficient, submerged, riders, liquid_type, delta)` (used by ice and by metal on slag) damps `velocity.y` relative to the liquid's own vertical speed, `WaterBasin.get_liquid_surface_velocity_y()` scaled by `submerged / rest_fraction` (clamped 0..1), so a block at its rest fraction follows a rising or draining level instead of lagging it, and the surface can't overtake a rider's swim probe. A rider can't hold the block back: in `_integrate_forces()`, while an actor touches the top face (`_rider_on_top`), no roof is hit and every rider has room above (`_riders_free_above`, a `test_move()` per rider in the physics step), a solver-reduced rise (`vel.y > _written_vy` with `_written_vy < 0`) is reset to the written velocity, and the rider is pushed up by its own depenetration. Under a ceiling the contact stops the block as before. The player completes it from its side by leading a rigid floor (see Rising rigid floors under Player). Dropping layer 1 from the block's mask does not work on a rigid body (a pair interacts if either side's mask matches), and a collision exception against the rider makes it fall through (below). **Don't use a collision exception against the rider** — Godot applies exceptions to both bodies, so the rider would fall through. Ledge-hangable via group `"ground"` (`hang_platform` is typed `PhysicsBody2D`, not `AnimatableBody2D`, for this reason; the hang follows the block's whole transform as it bobs, slides or tilts, `_follow_hang_platform()` mapping every pinned point through the platform's change of transform; `is_hangable()` is the block's say: a locked block always, a rotation-allowed one only within `hang_max_tilt_degrees` (10) of resting flat, at most `hang_max_speed` (90 px/s) and `hang_max_spin` (1.2 rad/s), refusing the grab otherwise and force-releasing a held hang (`_force_release_hang()` in `player.gd`, which also stops a mantle in progress); a melt releases a hanging player by clearing `is_hanging`, as `drop_platform.gd` does). While a player's hang is attached to the block (grab through the end of the mantle), the block and player hold a mutual collision exception (`_update_hanger_exception()`), dropped the frame the hang ends: the mantle tween carries the player's collider through the block's top corner, and without the exception the contact between them pushes the block while `_follow_hang_platform()` drags the mantle target with it, so the push can feed itself. **Any other actor-driven teleport onto a `CharacterBody2D` platform needs the same treatment.** Carried by conveyors: `_scan_contacts()` reads `get_conveyor_speed()` off the floor it rests on (ice and metal alike, regardless of slipperiness or weight) as carry, added to the written velocity but never to own motion; a block carried into a wall stops there, with no stored push-back left to creep it away. **Rotation** (`allow_rotation`, default true; false = locked upright): hand-integrated in `_integrate_forces()` like the rest. The solver's angular change (a corner landing, a ledge overhang) is accepted, then a soft spring pulls toward the nearest 90° (`righting_stiffness`) and angular drag (`angular_drag`, plus `angular_drag_liquid` scaled by the submerged fraction) damps it, so a block topples when its support goes but settles flat, upright or on its side. The centre of mass is lowered by `com_drop` (a fraction of half the height). The buoyancy couple lifts a tilted floating block's low side. Riders apply their weight straight down at their feet: a torque `lever_x * weight / gyration²` about the centre of mass (`_rider_torque()`, with `rider_load_tiles` setting how hard), cancelled while the block and its riders together balance over the floor contacts (`RIDER_SUPPORT_TOLERANCE`), so a rider near the edge of a supported block doesn't rock it or the blocks stacked on it, while a rider on the overhang of a perched block still tips it. Actor side contacts are classified in the block's upright frame and the shove guard's angular half only discards spin that increases angular speed beyond what was written. `save_state()` adds `angle` and `angular_velocity` unless the block is locked. Kicks act at the centre of mass (linear velocity only), so a block slides rather than topples. Actors can never shove it: kinematic bodies hand a rigid body velocity through the contact solver, so the shove guard in `_integrate_forces()` (`reject_actor_shove`) removes any horizontal speed an actor's side contact gave it away from that actor, and the displacement it caused; walking into a block, or a block sliding into an actor, just stops it, so it only moves under its own motion. A block it hits is pushed by the contact in proportion to `mass`.

Positive angle, torque and speed are clockwise on screen.
  - **Riders**: engine moving-floor carry plus an **idle grip**: an actor standing still on it (own `|velocity.x|` under `IDLE_SPEED`, on the floor, the body directly beneath) is pinned each frame at its **foot point** (the lowest point of its upright collider) in the body's local space, then snapped onto the face along the face normal (up to `SNAP_TO_FACE`); an actor moving under its own power is released to engine carry and re-anchored once idle. `grip_idle_riders` turns the grip off. Carry alone drifts riders toward the descending end every swing, and anchoring the collider centre slides the feet, hence both parts and the foot point. Rigid blocks are never gripped: they ride by engine contact and their own carry assist.

Loads stack: what rests on a block that rests on the body counts at its own x (up to `MAX_STACK_DEPTH`). A load that counted last frame and is still in the band keeps counting for `LOAD_LATCH_FRAMES` after the test starts failing, so a contact glitch doesn't zero the torque. Torque is `weight × (load x − pivot x)`. `get_loads()` entries are `body`, `id`, `weight`, `offset`, `torque`, `position`. `get_net_torque()` is loads plus resting liquid; `get_load_torque()` and `get_liquid_torque()` are its parts.
  - **Dynamics**: torque = loads + liquid + motor − `restoring_torque` × angle (the spring back to level, ignored with `free_rotation` and while the motor runs); angular velocity gains torque / `inertia` × delta, loses `damping` (fraction per second), then `friction_torque / inertia × delta` off its magnitude without crossing zero, so a body at rest under a net torque below `friction_torque` stays put. Without `free_rotation` the angle is clamped to `min_angle_degrees`..`max_angle_degrees` (default ∓25; keep them around 25 or less so riders hold) and velocity into a stop is zeroed, with no bounce; with it the angle wraps to ±π. Loads don't add to inertia (their weights are in torque units where gravity is 1). Defaults (`inertia` 120, `damping` 1.5, `friction_torque` 8, `restoring_torque` 60) are tuned by feel for the 2-tile plank; tune per instance.

See the Liquid system for the carry and weight.

With `free_rotation` it is a steady drive. - **Liquid system** (`water_manager.gd`, one instance per level scene — not an autoload; `WaterBasin` in `basin.gd`; `WaterFaucet` in `faucet.gd`; `LiquidConstants` in `liquid_constants.gd`, renamed from `water_constants.gd` once a second liquid existed): flowing liquid is pooled particles — position/velocity/type in parallel arrays, no per-particle nodes or collision shapes — sized by `LiquidConstants.ACTIVE_PRESET` (particles-per-tile/pixel-size/volume all cascade from one preset constant, shared by every liquid type; the active value is still being tuned, so read it from `liquid_constants.gd` rather than trusting a number written here). Each particle also carries a `LiquidConstants.LiquidType` (`WATER`, `SLAG`, or the gas-only `STEAM`); every physical property that differs by liquid — creep speed, bounce, friction, push force, hazard, color, lifetime — is read per-particle from `LiquidConstants.profile(type)`, so the simulation itself has one implementation regardless of which liquid is flowing. Each physics frame every (non-`STEAM`) particle raycasts against the tilemap and any `"water_solid"`-registered body — **except catwalk tiles, which water ignores entirely** (a hit on a cell whose `surface_type` is `"catwalk"` is stepped past and the ray re-cast from just beyond it, up to 4 passes, in `_cast_ignoring_catwalks()`; so water falls through them, never rests on, bounces off or creeps along one, while they stay solid for the player) — (moving platform, drop platform, crusher's `ArmBody`, cannon's `StaticBody2D`, the see-saw, and a basin's own solidified crust — see below), bounces or slide-creeps depending on impact speed and its own type's profile, and is absorbed into whichever `WaterBasin` its column belongs to once it reaches that basin's current surface height. A `WaterBasin` is a hand-placed `@tool` node (same placed-and-sized-by-hand convention as the conveyor belt) with its own `liquid_type`; it samples the tilemap's actual per-tile collision geometry under it at edit time (counting only ground-like tiles, `"ground"` and `"glass"`, as floor and wall, never catwalks) to derive a per-column floor height (fractional on sloped/half-height tiles) and treats its two end columns as walls. `fill_volume` and the crust's two faces (`crust_top_row`/`crust_bottom_row`) are the only things mutated at runtime: a same-type particle reaching a not-yet-full, crust-free basin credits `fill_volume`; an OPPOSITE-type particle reaching a basin that already has some settled liquid instead solidifies a slice of it into a crust and emits steam — the "water meets slag, or vice versa" reaction. **Steam**: `WaterManager.emit_steam(world_pos, amount)` is the only entry point (`amount` is the volume in tiles that reacted); the crust reaction calls it, once for the crust's formation and once for every opposite-type particle that reaches a crust's top face, starting the puff at the particle's x and no lower than half a particle above the crust (`_steam_origin()`). It makes `amount` × `STEAM_PUFFS_PER_TILE_VOLUME` (16: one puff per arriving particle at the 16-per-tile preset, rounded at random, so a stronger faucet makes a denser column) `STEAM` particles, each rising at a constant `STEAM_RISE_SPEED` (80 px/s, ±`STEAM_SPEED_JITTER` 10%) inside a ±`STEAM_CONE_DEGREES` (6°) cone about straight up, with no gravity or deceleration, so a column is `STEAM_COLUMN_HEIGHT` (rise speed × `STEAM_LIFETIME` 1.6 s = 128 px, 8 tiles) tall in the open. Each steam particle casts one ray a frame and dies on the first solid it meets (the world tilemap or a `"water_solid"` body; catwalk tiles are stepped past as for liquid), so a column stops at a ceiling; steam is only emitted while `STEAM_POOL_RESERVE` (256) pool slots are free, so it can't starve the liquid. Steam isn't saved: after a restore a column rebuilds over about one lifetime. **Steam lift query**: `WaterManager.get_steam_lift(rect, previous = 0.0, delta = 0.0) -> float` is a 0..1 coverage of a world-space rect (the board's footprint) by steam. Steam particles within the rect's height count by the horizontal span they cover, merged over at most `STEAM_LIFT_MAX_BINS` (32) equal bins of the rect's width, so a dense column reads the same as a thin one of the same width and the reading depends on neither the particle preset nor the rect's height; coverage of `STEAM_LIFT_FULL_COVERAGE` (0.5) of the width reads 1. The raw reading is noisy, so a caller passes its previous smoothed value and the frame time and gets `max(reading, previous - delta / STEAM_LIFT_DECAY_TIME)` back (instant rise, linear decay over `STEAM_LIFT_DECAY_TIME`, 0.3 s, like the surf's wetness); with the defaults it is the raw reading. It is stateless (the manager keeps no per-caller value), only steam counts, and the surfing player is its only caller (see Steam lift under Surf). The `debug_steam_lift` export (default false) shows an on-screen readout of the raw and smoothed values for the player's current collider rect. The numbers are placeholders to be retuned against the surfer's lift (see Steam lift under Surf). Crust is stored geometry (a top and bottom row across the wet columns), rigid and walkable via a runtime `StaticBody2D` with one rectangular collision shape per column. It forms once at a fixed 0.75-tile thickness (`CRUST_THICKNESS_TILES`) and never moves, grows or thins afterwards, and nothing is ever absorbed *through* it — same-type liquid arriving on top just rests on the crust, while an opposite-type particle evaporates into a steam puff on contact. A basin reads as full once its outer surface (the liquid, or the crust's top face if crusted) reaches its shorter wall's height, at which point arriving same-type particles creep out over that wall using the ordinary ground-creep rules — this is also how basins chain into each other with no adjacency data at all. An optional `initial_fill_depth_below_surface` authors a basin as starting partway (or fully) full. `SLAG`'s profile is marked hazardous: both flowing slag particles (within `PLAYER_PUSH_RADIUS`) and a settled slag basin's still-liquid surface (not any crust that's formed over it — crust reads as safe, walkable ground regardless of which liquid reacted to form it) call `take_hit()` on the player each frame of contact, and the player swims in a hazardous basin's liquid with buoyancy and takes damage each frame. The settled body draws as a real per-column staircase polygon (crust between its two stored faces, liquid from its own floor-anchored surface down to the seabed, distinct colors for each; any gap between them after a drain is a void and is simply not drawn; a skinned liquid's body is drawn as one filled rectangle per ripple strip, not a polygon, because `draw_colored_polygon()` triangulates all-or-nothing and a ripple's whole-pixel staircase could occasionally be rejected, blanking the whole body for a frame — unskinned liquid and crust, whose tops are flat, still draw polygons, and `debug_check_body` on a basin warns whenever the polygon form of the body would fail to triangulate); slag, water and every crust are skinned with art from `sprites/liquids/` (per liquid type: `SKIN_BY_TYPE` for the surface, with water looping faster than slag, and `CRUST_SKIN_PATH_BY_TYPE` for the crust, so water can cool from water colour; a missing file falls back to flat colour / the slag crust art) — the art is the top layer; a liquid's body below it is the art's bottom-row colour, while crust art has its non-neutral fringe cut transparent so the liquid shows through it, or over a drained void only the fringe inside the crust is filled neutral and the underside keeps the art's own jagged edge (see `LiquidSkin` and the Skins note and Crust rendering in `water-mechanic.md`); everything is drawn behind the tilemap so any approximation at a sloped tile's edge stays hidden. Moving particles push the player horizontally within a small radius of them (`PLAYER_PUSH_RADIUS` — currently reads too large, flagged for retuning), summed by direction and capped both by a flat ceiling and by whichever contributing particle is currently fastest, so a crowd of slow particles can't shove the player faster than the liquid is actually moving. `WaterFaucet` is tile-anchored (node origin at its tile's top-left, `spawn_offset` picks the spawn point inside the tile) and emits particles at a per-instance `flow_rate` (volume per second, independent of the particles-per-tile preset) while `is_open`. Sitting on the floor tile of a basin's interior column, it is a **drain**: each drip debits `PARTICLE_VOLUME` from that basin's `fill_volume` and spawns a particle of the basin's liquid type, leaving any crust hanging over the void it opens; nothing comes out once no liquid lies over the tile. Anywhere else it is a plain **source** dripping its own `liquid_type` (water or slag); the melt burst API (`spawn_melt_particles(tile_pos, liquid_type, world_center = INF, cell_rotation = 0)`, covering both ice→water and metal→slag) is called by `MeltableBlock._melt()` once per 16px cell it covers; with a finite `world_center` the burst is spread over the cell in the block's rotated frame, inset by `SPAWN_INSET` (0.85) so every particle starts inside the block's volume, otherwise over the snapped, axis-aligned tile. **Carry and load**: a particle resting on a registered body is carried by that body's whole transform change: each frame `_solid_motion` maps every body whose `global_transform` changed (`_registered_solid_prev_xform` holds last frame's) to `new × old.affine_inverse()`, and a resting particle's position is mapped through it, so a platform's translation carries it and the see-saw's rotation swings it round the pivot; particle velocity is untouched. `forget_motion(body)` resets a body's stored transform so a teleport (a checkpoint restore) isn't carried. A resting particle on a registered body that has `get_pivot_global()` (a `RotatingBody`) also loads it: `LiquidProfile.weight_per_tile_volume` (block-mass units per tile of volume: water 1.0, the same as ice; slag 3.0, under metal's 4; steam 0) × `PARTICLE_VOLUME` × the particle's horizontal offset from the pivot, summed per body each frame and read through `get_resting_torque(body)`; particles on a basin's synthesized surface add nothing. **Surface velocity**: `WaterBasin.get_liquid_surface_velocity_y()` (px/s, negative = rising) is what a floating block rides. It is estimated from the change of `get_liquid_surface_world_y()` between physics frames, smoothed over `SURFACE_VELOCITY_SMOOTH_TIME` (0.25 s, since fill arrives in particle-sized steps) and clamped to ±`SURFACE_VELOCITY_MAX` (240), lazily and once per physics frame however many bodies ask; the first query, or one after more than `SURFACE_VELOCITY_GAP_FRAMES` (3) frames without a query, reads 0 and restarts the estimate, so a restore or a teleported fill can't read as a flood. Runtime scratch only (`_surface_vy`, `_surface_prev_y`, `_surface_vy_frame`), never saved; ripple isn't part of it. **Surface ripple** (cosmetic, in `basin.gd`): a per-basin wave simulation over 4px samples bends only the drawn top edge of the settled liquid, driven by `WaterBasin.disturb(world_x, velocity, radius)` from landing particles, drain drips, player swim entry/wake and ice/metal block splashes. Viscosity is per-liquid data in `LiquidProfile` (`ripple_speed`, `ripple_damping`, `ripple_strength`): slag's waves are slow, heavily damped and weakly stirred. It costs nothing while calm and never affects `fill_volume`, queries, collision or crust. See `water-mechanic.md` for the full data-flow/API/tuning-constant reference and what's still open. A surfing player reads the liquid through two pull queries, `get_floor_wetness()` and `find_skim_basin()`, and a basin raises a runtime one-way skim floor for it on layer 3 (see the Water bullet under Surf and `water-mechanic.md`). **Laser boiling** (roadmap 5.4): `WaterManager.boil_along_beam(points, delta)` boils the WATER of every `boilable` basin a beam polyline crosses, emitting steam at the crossing and draining the basin at its `boil_volume_scale` (see Laser turret); `BOIL_STEAM_VOLUME_PER_SEC`, `BOIL_DRAIN_VOLUME_PER_SEC` and `BOIL_ENTRY_NUDGE` are untuned placeholders. `WaterBasin` gains the authored exports `boilable` and `boil_volume_scale`. **Electrified water**: a Spark (see Rail bot) or an Arc (see Arc turret) reaching the settled surface of a crust-free WATER basin electrifies the whole pool for `electrified_time` (default 1 s, exported; a later strike restarts the countdown, never adds to it). `WaterBasin.try_electrify_at(world_point)` is the only entry (it applies the refusals listed under Rail bot, then sets the runtime `_electrified_left`, kicks a cosmetic ripple through `disturb()`, plays `interactive/basin_zap` at the surface and returns true); `is_electrified()` reads it and `is_hazardous_now()` (a hazardous liquid, or electrified) is the one question the player's swim check and `WaterManager.find_skim_basin()` ask, so a future transient hazard goes there and nowhere else. `conducts_sparks` (default true) and `electrified_time` are authored exports; the countdown is runtime-only and **not saved**, so a restore comes back calm. While electrified the pool is hazardous like slag but only to a submerged player (`ELECTRIC_CONTACT_DAMAGE`, 1 per `take_hit()`, paced by its i-frames, in every held state), and a surfer cannot skim it (no skim floor is raised, so a board over it falls in, ends the surf and is hurt). It affects nothing else: floating blocks, flowing particles, the basin sensor and power circuits do not read it. The look is placeholder code in `_draw_electric()` (flickering tint, bright surface line, zigzag arcs, a bolt at the strike point, tapering over the last `ELECTRIC_FADE_TIME`); `_process` stays on while it runs.

- **Checkpoint and save/restore** (`res://scripts/game.gd` autoload `Game`; `res://scenes/interactive/checkpoint.gd` + `checkpoint.tscn`): a checkpoint stores an in-memory snapshot of every saveable node; dying or pressing `R` reloads the level and re-applies it.
  - **Saveable contract**: a node joins group `"saveable"` in its own `_ready()` (never deferred — the restore runs before deferred work) and implements `save_state() -> Dictionary` (plain data only: bool/int/float/String/Vector2/Array/Dictionary, nothing referencing nodes or resources) and `load_state(d)`. `load_state` runs on the freshly loaded node after its `_ready()`, so it must snap (no animation, sound or edge event) and must not depend on any other saveable having been restored first. Snapshot keys are node paths relative to the scene root, so renaming or moving a saveable in a level just starts it fresh. A node that frees itself (gem, melted block, dead enemy) is absent from the snapshot, and `Game.apply()` frees the fresh copy of any saveable with no entry — such nodes only describe their alive state and need no "was I freed" flag. The snapshot belongs to the level id it was taken in and is discarded when another id is loaded (`has_checkpoint()` is false elsewhere, and `Game` ignores a moment with no level); nothing is written to disk.
  - **`Game` API**: `checkpoint_index` (-1 = none), `checkpoint_position`, `has_checkpoint()`, `commit_checkpoint(index, respawn_position) -> bool` (snapshots and stores the position only if `index` is strictly greater than the current one, then emits `checkpoint_committed(index)`), `clear_checkpoint()`, `capture()`, `apply(scene_override = null) -> bool`, `respawn()`, `restart_level()`; signals `snapshot_captured`, `snapshot_applied`, `checkpoint_committed`.

A level Godot started itself (the main scene, F6 in the editor) is **adopted** lazily by `_ensure_adopted()` (also queued from `_ready()`): its source is its own `scene_file_path` and its id the catalog row with that path, else a `path:` id from `LevelCatalog.id_for_path()`; a root with no file can't be reloaded. `LevelCatalog` is the built-in provider: `entries()`, `entry()`, `source_of(id)` (a row's path, or the path inside a `path:` id), `id_for_path()`, `next_after(id)`; `Game.next_level_id(override_path)` returns the `Finish` override's id if given, else `next_after(current_level_id)`. Live pitfall: the restore must still hang on the new root's `ready` signal and the checkpoint scope on `current_level_id`; both are set before `add_child()`, because checkpoints read `Game` in their own `_ready()`.
  - **Respawn flow**: `respawn()` (from `R` and the player's death timer) reloads the current level; if a checkpoint exists it also `apply()`s the snapshot and calls the player's `respawn_at(checkpoint_position)`, otherwise the reload is the level's initial state. The restore runs from the new level root's `ready` signal (connected in `Game._swap_level()` before the root enters the tree, so it needs no path matching): that fires after every node's `_ready()` — all saveables have joined their group — but before any deferred call queued by those `_ready()`s. Restored buttons therefore reach circuits and `PowerTarget`s before their first recompute, and wired devices snap through `set_powered_initial()` with no sound or animation; a wired device re-derives from its restored source rather than trusting its own saved frame. A second `respawn()` while a load is under way is ignored. After the player has won (`is_dancing`), `R` calls `restart_level()`, which clears the checkpoint first ("play again" starts from scratch). Music never restarts: `Audio.play_music` returns early when the requested track is already playing, and `Audio` is an autoload.
  - **What each type saves**: gem nothing; button `active`, `pressed` and, for a timed one, `time_left` (for 3 physics frames after restore an empty sensor doesn't clear `pressed`, so a block resting on a restored toggle button isn't read as a fresh press; `powered_changed` is emitted only if `active` changed); speed trap `powered`, `time_left`, the reading and whether it passed; door `want_open` and exact frame (a door caught mid-travel resumes); `MeltableBlock` position, horizontal velocity and `melt_progress` (vertical velocity is dropped so a restored fall speed can't fire a false splash); laser turret `enabled`; arc turret `enabled`; mirror accumulated target rotation and last power level; moving platform phase within its loop and the running flag (the tween is rebuilt and fast-forwarded in 50ms slices, since a `Tween` can't be seeked); crusher clock, segment, powered, parked and jammed flags; see-saw `angle`, `angular_velocity` and `motor_dir`; drillbot position, facing and health (a bot saved mid-dwell resumes walking and restarts the dwell at its patrol end); stingbot position, health, phase, all five timers and facing; basin `liquid_type` (an empty basin is claimed by whichever liquid arrives first, so it can differ from the authored export), `fill_volume`, `has_crust`, `crust_top_row`, `crust_bottom_row` (crust set first, since the fill limit depends on it; collision rebuilt, ripple cleared); player `gems_collected`, `gems_total` and `points` only (position and health come from `respawn_at()`).
  - **Not saved**: in-flight liquid particles, bullets, arcs and explosions (cleared by the reload, so a basin mid-overflow comes back settled); the drop platform (always returns armed at its original spot); faucets, conveyors, cannons, sawwheels, jump pads and the finish, which re-derive from restored power and gem state; checkpoints themselves.
  - **Checkpoint** (`checkpoint.gd`, `Area2D`, layer 0, mask 1): `sprites/interactive/checkpoint.png`, 16×112 = 7 frames on one `Sprite2D` (`vframes` 7), frame 0 inactive, 6 lit, a light climbing the pole between; node origin is the centre of its 16×16 tile. `order` (exported) is assigned automatically when an instance is added to a scene in the editor — the lowest whole number from 1 up that no other checkpoint in the edited scene uses, so sequential adds get 1, 2, 3 and a number freed by deleting a checkpoint is reused by the next one added; it stays hand-editable, instances already saved in a level are never renumbered, and a duplicate or paste is numbered like any new node (the script is `@tool` only for this: in the editor `_ready()` numbers a node whose `owner` is still null, meaning it was just added, and returns before touching the `Game`/`Audio` autoloads, which don't exist there; the root of `checkpoint.tscn` itself is skipped). A touch counts only if it is greater than `Game.checkpoint_index`, so a later checkpoint overrides an earlier one and never the reverse; two checkpoints in one level sharing an `order` get a warning, and would light together (the second can never override the first). The sensor is polled every physics frame, so a player already inside at load still counts; a dead or dancing player never activates one. Activating calls `Game.commit_checkpoint(order, global_position + respawn_offset)` (`respawn_offset` default `(0, -1)`: the player's capsule is 16px tall and centred, so the tile origin puts its feet on the tile's bottom edge) and plays `interactive/checkpoint` (listed in `Audio.PLANNED` until a file exists). A checkpoint is lit while its `order` is at or below `Game.checkpoint_index`: on `checkpoint_committed` every checkpoint in that range animates 0→6 at `anim_fps` (12) if it isn't already lit, so earlier ones stay lit and skipped ones light up with it (only the touched one plays the sound); a level that loads onto a restored snapshot starts with all of them already lit, silently. Place it before the Player in the level tree so the player draws in front.
  - **Live pitfalls**: a new saveable must join the group in `_ready()` (not deferred) and its `load_state` must be silent and order-independent; anything that recounts or caches level totals at load (like `gems_total`) must survive the restore having already freed collected objects; `load_state` on anything a power source drives must tolerate `set_powered_initial()` running afterwards and winning.

## Roadmap: before level design and level loading

No required steps remain before level design and the loading entry point (see Level editor seams). The items below are deferred or unplanned; when one is taken up it follows the working rules and shared rules of the cross-mechanic numbering: one editor-confirmable step per turn, fold the result into the Player or World sections and delete its bullet here, update `export-audit.md`, add sound ids to `Audio.PLANNED`.

**Deferred (important, not blocking)**
- **Camera at speed**: lead in the travel direction and handle fast falls; first check it at speed in a real level.
- **Surf landing bonus and scoring**: a clean tilt match at touchdown could give a small speed bonus, and landing on a downhill could convert fall speed into forward speed, which makes dips and half-pipes chainable (the top-speed cap guards against pumping exploits). `add_points()` could reward air time, bowl chains and skim distance; gems along launch arcs double as guides.
- **Refine the ice-block underside push** (see the open tuning item in the Ice block bullet).

**Noted, no plan**
- Side-dependent mirror rotation (`kicked()` could carry the direction).
- Weight for riders other than the player and `MeltableBlock`s (enemies are weightless).

## Current status

Everything described above is built and confirmed in-editor, including checkpoints (the full die-and-restore pass and the finish's unlock state after a restore), swim, draining and the surface ripple, the points system, the medkit and the health bar's gain animation, the parallax backdrop, `dance_through`, gem trails, the basin sensor and the crust hang entries. Standing caveats:

- No sound files are authored yet. The hooks are verified silent, and every id is in `Audio.PLANNED`.
- Much of the art is placeholder drawn in code: the grunt, breakable barrier, metal block, speed trap, receivers, sensors, plates, bullet target, surfboard, see-saw plank and the level-complete overlay.
- Numbers still to tune by eye: the surface ripple's wave constants and the steam-lift exports and decay time.
- A `RotatingBody` with more than one collision shape (a T) is untested.
- The grunt's behaviour (see Grunt under World objects) is built but not yet confirmed in-editor; its art is rectangles.
- The rail bot (see Rail bot under World objects) is built but not yet confirmed in-editor; its art is shapes drawn in code. Check in particular: a rail drawn with the Path2D tool (as a child, and via `rail`), ping-pong and a closed loop, the drip telegraph and the spark's fall speed against the player's run and jump, a spark rolling down a slope and along a belt (feel of `FLAT_RESISTANCE`, `SLOPE_RESISTANCE`, `BELT_GRIP`; the rolling and belt carry were checked headless against the real belt and rail bot, not by eye), a spark landing on an ice or metal block (the block's contact scan reads a layer-0 body as an actor, so it should never be pushed), twitching where a belt pins a spark against a wall, a laser and a mine blast destroying it, a button stopping it, and a checkpoint taken mid-ride. Electrified water (see the Liquid system) is checked headless (a spark falling onto a pool, the hazard to a submerged player, the skim refusal, and the refusals for slag, a crust, a wall column and `conducts_sparks` off) but not by eye: check in particular the placeholder look and flicker, the splash and strike point, how 1 s of electrification feels against a rail bot's 1.6 s drip over a pool, a swimmer being hurt and a surfer dropping in, and a spark landing on a floating ice block and rolling off into the water.
- The arc turret (see Arc turret under World objects) is built but not yet confirmed in-editor; its art is shapes drawn in code. It is checked headless (the firing interval and the telegraph's timing, a reflection off a `Mirror` at 45° onto a player stub, passing through a layer-1 body, stopping on a wall and on the back of a mirror, `arc_range`, a reflected arc ending on its own turret, power on/off/initial, save and restore, and electrifying a basin in level 1-1 with `conducts_sparks` on and off) but not by eye. Check in particular: the arc's speed (220 px/s) and the 0.45 s telegraph against the player's run and jump, the crackle look, a rotating mirror turning in front of an arc in flight, an arc on a see-saw plank mirror, an arc bouncing between two mirrors, an arc over a pool with and without a crust, a swimmer in a pool an arc has electrified, and a checkpoint taken while an arc is in flight.
- The proximity mine (see Proximity mine under World objects) is built but not yet confirmed in-editor; its art is shapes drawn in code. Check in particular the trigger and fuse feel (is 0.8 s with a 32 px trigger escapable at running speed?), a kicked mine detonating on a Grunt and on a wall, a chain of two or three mines, and a checkpoint taken while one is armed.
- The Drillbot's free patrol (`patrol_distance` 0, see Drillbot) is built but not yet confirmed in-editor. Check in particular that the drill's tip stops at a wall rather than burying into it, that it turns at a ledge with its drill flush to the edge (not hanging out, not turning too early), on a slope up to a wall, on a slope, on a one-tile platform, and after a checkpoint restore.
- The air kick (see Kick) is built but not yet confirmed in-editor. Check in particular: kicking at the top and at the start of a jump, kicking out of a swing release and a jump-pad launch, that a kick right before a ledge or catwalk grab behaves, that the kick animation reads in the air, and landing during the animation.
- The tread crawler (see Tread crawler under World objects) is built but not yet confirmed in-editor; its art is shapes drawn in code. Check in particular that a landing on top flips it reliably (including from a jump pad or a surf), the stomp bounce feel, and that a crawler on a narrow platform doesn't jitter.
- Touch controls (see Touch controls under World objects) are built but not yet run: not confirmed in-editor, the web build or on a device. Layout, button sizes and the D-pad sectors are first guesses to tune on a real phone.
- The level loading entry point (see Level loading) is built but not yet confirmed in-editor, including `test_level_2` (a small floor level with two gems, a checkpoint and a finish, chained after `test_level` by catalog order). `test_level` has no `Finish` yet.

**Not yet built**: the deferred items under Roadmap: before level design and level loading, step 7.2 of Roadmap: cross-mechanic interactions, level content beyond the test levels.
