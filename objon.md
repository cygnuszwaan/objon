# Objon — 2D tilemap puzzle-platformer (Godot 4.x, GDScript)

Godot 4.x, Compatibility renderer, GDScript only (no C#/.NET). Claude can run Godot 4.4 headless in its sandbox (the release zip downloads from github.com; wrap the project files in a minimal `project.godot` with the `Audio` and `Game` autoloads and the input actions, and run test scenes as the main scene, since `-s` scripts don't see the autoloads), which checks logic, signals and numbers but not rendering or feel — nothing here counts as verified until the user confirms it in their own editor.

## How to maintain this file

**This file and the topic files under `docs/` describe the project as it currently stands, not how it got there.** They are not a changelog, a development diary, or a decision log. When something changes:

- **Update the relevant section in place, in the file that owns it (see the docs index).** Don't append a dated/numbered entry describing the change — rewrite the description of the system itself so it reads as if it had always worked this way. If a fix corrects an earlier bug, the bug and its history are not worth keeping once the fix is in and confirmed; just describe the correct behavior.
- **Only keep a pitfall if it's still a live risk.** A bug that's fixed and stable doesn't need a paragraph of "here's what went wrong and how it was diagnosed" — that's narrative, not a fact about the current system. A pitfall belongs in this file only if a future change could plausibly reintroduce it (e.g. "every hang-start function must set `hang_style` explicitly, or it leaks from the previous hang").
- **Prefer deleting over accumulating.** If a fresh read of the current code contradicts something written here, replace the claim — don't leave both the old and new version in the file "for context." If a whole section stops being true or useful, cut it rather than marking it stale.
- **Keep `export-audit.md` current.** It logs which scripts have been checked against the "runtime code never writes an export" rule (see Level editor seams). Update it whenever you audit or change an object, and add any new script to it. `audit_export_writes.py` re-runs the scan from the project root. It is the one deliberate exception to "describe the project as it stands": a work log that is deleted once the final pass is done.
- **Finishing a roadmap item** has two stages, because the designer-facing files describe only what is confirmed. The same two stages apply to any change that adds or alters an object, mechanic or contract a level designer can use, whether or not it has a roadmap entry.
  - **Stage 1, when built** (the session that writes the code): the owning topic file describes it as it stands, with a `## Status` line saying it is built but not yet confirmed in-editor; any contract, group or invariant it adds is written into the core, once; the sound ids are in `Audio.PLANNED` and the script is in `export-audit.md`. Its entry in `docs/roadmap.md` **stays**, with one line added at the top of the entry (`Built, awaiting in-editor confirmation; see Status in <topic file>.`), so the item id can still be found. `docs/level-design.md` and `docs/puzzles.md` are **not** touched yet. Run `python3 check_docs.py`.
  - **Stage 2, when the user has confirmed it in-editor** (a separate step, usually a later session; the user says which item and which puzzle concepts, if any, they have actually tried): delete the `## Status` line; delete the item's entry from `docs/roadmap.md`; in `docs/level-design.md` add its catalogue entry (knobs, what it reacts to, what it affects, gotchas), its row or column in the Interaction matrix if it touches other systems, and remove any limit it lifts from Gaps, limits and gotchas; in `docs/puzzles.md` add any new primitive it makes possible and any new or revised concept, marked **(untested)** unless the user has tried it, and remove the mark from any concept the user confirms. Run `python3 check_docs.py`; it warns about a scene that `docs/level-design.md` never names.
  - If the user reports a problem at Stage 2, the item goes back to Stage 1: fix it, keep the Status line and the roadmap entry, and finish only after the next confirmation.
- **Keep this file the core.** It holds only what every session must read: setup, layers and groups, the level-editor seams, the contracts, the cross-system invariants, the docs index, the roadmap and the project-wide status. System detail belongs in a topic file under `docs/`. If this file grows past about 10k tokens (40 KB), move something out.
- **Index every topic file.** A new file under `docs/` goes in the docs index with the names of the bullets it holds, and ends with a `Reads with:` line naming its neighbours. Run `python3 check_docs.py` from the project root: it fails on an indexed file that is missing, a file that is not indexed, or a file that does not end with a `Reads with:` line naming files that exist.
- **Cross-references name a bullet, not a file** ("see Arc turret"). The docs index says which file holds each name; when a bullet moves, update the index rather than every reference. Older text that says "under World objects" or "under Player" means "in the topic file that holds that name".
- **A cross-system rule goes in the core, once.** A new contract or invariant that other systems must respect gets one line in the lists below, pointing at the topic file that has the detail. Don't copy the detail here.
- **Status lives with the system.** A "built but not yet confirmed in-editor" note goes under a `## Status` heading at the end of the topic file that owns the object (before its `Reads with:` line), and is deleted once confirmed; only project-wide caveats stay in Current status below.
- **When in doubt, ask: would a system prompt for this project want this sentence?** A system prompt states facts and constraints; it doesn't tell stories about how they were discovered. That's the target register for this whole file.

## Project setup

- Godot 4.x, Compatibility renderer (for touch/mobile support), GDScript only.
- Viewport 1280×720. `Camera2D` is a child of `Player`, zoom `2.5,2.5` (source art is 16px sprites; zoom rather than sprite scale keeps pixel-perfect rendering; the view is 512×288 world px). Default Texture Filter is **Nearest**, set project-wide.
- **Script placement**: each `.gd` lives next to the `.tscn` it belongs to (e.g. `res://scenes/player/player.gd` beside `player.tscn`) — not centralized. `res://scripts/` is reserved for things that belong to no single scene (autoloads, shared helpers) — currently `Game` (an autoload holding the checkpoint snapshot and the respawn flow, handling `R` and owning the pause menu), and `LaserBeam` (`laser_beam.gd`, a stateless beam-solver helper used by every laser turret and every arc — see the laser bullet under World objects), and `MeltableBlock` (`meltable_block.gd`, the base class of the ice and metal blocks — see the Meltable block bullet under World objects), and `SurfaceTypes` (`surface_types.gd`, static helpers that define what a tile's `surface_type` means — see the Tilemap bullet), and `LevelCatalog` (`level_catalog.gd`, the playable levels as data, in play order — see Level loading under Checkpoint and save/restore). and `TouchControls` (`touch_controls.gd`, the on-screen controls `Game` adds as a child — see Touch controls under World objects).
- **Folder convention**: `scenes/{player,enemies,interactive,traps,levels,ui}/`, `sprites/` (subfolders per kind, `backgrounds/` for parallax art), `audio/`, `resources/` (`.tres` assets shared by more than one scene, tilesets included: a tileset used by several levels is saved here rather than embedded in each level, so every level shares the same tile data, `surface_type` custom data and collision shapes). `enemies/` = things with behavior/AI/health; `interactive/` = things the player acts on or rides (jump pads, conveyors, ladders, platforms, buttons, doors); `traps/` = things that act on the player (saw, crusher, spikes, cannon); `collectibles/` = things the player picks up.
- **Physics layers**: layer 1 = **actors** (any `CharacterBody2D` walking under its own `move_and_slide()` — Player, Drillbot); layer 2 = **world** (solid environment an actor can stand on or be blocked/pushed by — ground tilemap, `drop_platform`, `moving_platform`, `Crusher`'s `ArmBody`, `Cannon`'s `StaticBody2D`, `RotatingBody`). New actor: always mask layer 2; mask layer 1 too only if it should be solid against other actors (default: no, to avoid enemies pushing each other around). New solid platform/hazard body: layer 2, whether it moves or not. **Exception — anything the player should be able to kick (`Mirror`, `IceBlock`, `MetalBlock`) or bowl through with the surf (`BreakableBarrier`) sits on layers 1|2:** `KickHitbox` keeps the default mask (layer 1 only) and hits the target's physics body directly, and the bowl sweep queries layer 1 too, so a layer-2-only body is invisible to both; layer 2 keeps it solid like the rest of the world. Keep that pairing if either body's layers are ever changed. **Layer 0 with mask 2 = a body that collides with the world and that nothing else can see** (`Spark`: no query, sensor or contact filter on layer 1 or 2 finds it). **Layer 3 = the basin skim floor** (`WaterBasin`'s runtime one-way floor under a skimming surfer): only the player's mask includes it, so particles and blocks never see it. Pure-trigger `Area2D`s (gems, `Sawwheel`, `Crusher`'s root, `DrillHazard`, `KickHitbox`, `Bullet`) are unaffected — they stay on the default layer/mask unless they specifically need to detect something outside layer 1 (`Bullet` masks layers 1|2 so it also detects world tiles, not just the player). **`Area2D` never blocks movement, regardless of layer/mask** — it's a trigger only. A trap that also needs to be stood on (`Cannon`) needs a separate `StaticBody2D` on layer 2 for the solid part; the `Area2D` hazard, if any, is layered on top of that.
- **Groups in use**: `"player"` (added by `player.gd` in its own `_ready()`, not baked into `player.tscn`, so a node whose `_ready()` runs earlier in the level tree finds nothing: look it up again later, as `WaterManager` does every physics frame while its reference is null), `"trap"`, `"ground"`, `"catwalk"` (a body, or a whole catwalk `TileMapLayer` kept apart from the ground layer: the player's hang probes, the ladder landing and the laser accept anything in it as a catwalk, and water passes it because it is not `"world_tilemap"`), `"world_tilemap"` (the walkable ground `TileMapLayer`), `"ladder_tilemap"` (the separate ladder layer), `"water_manager"` (each level's `WaterManager` instance, looked up by basins/faucets/the player), `"water_solid"` (non-tilemap bodies water particles collide with and can be carried by — moving platform, drop platform, crusher's `ArmBody`, cannon's `StaticBody2D`, laser turret's and arc turret's `Body`, the laser receiver, the bullet target, the see-saw, the breakable barrier, ice blocks while intact), `"laser_mirror"` (every `Mirror`, and a see-saw with `mirror_surface` on; what `LaserBeam` iterates to find reflectors), `"power_target"` (every `PowerTarget`; how a conductor layer finds devices at its terminals), `"power_source"` (every button, speed trap, laser receiver, arc receiver, bullet target, weight plate, angle sensor and basin sensor), `"gem"` (every gem; the player counts the level's total from it at load), `"swing"` (every `Swing`; what the player's grab looks up), `"grab_rail"` (a `Path2D` the player can hang from: a `Rail` node joins it at run time, as does a rail bot's rail; a plain Path2D with no bot is added by hand), `"rail_bot"` (every rail bot; the player's rail hang treats it as an obstacle), `"saveable"` (every node that takes part in checkpoint snapshots — see Checkpoint and save/restore), `"checkpoint"` (every checkpoint), `"hazard_layer"` (every `PoweredSpikeLayer`; the player's hazard poll reads each one that answers `is_hazard_active()`).
- **Tilemap**: `TileMapLayer` node (not the older `TileMap`). A `surface_type` String custom-data layer on the `TileSet` marks `"ground"`/`"glass"`/`"catwalk"` cells (glass: solid and unbreakable, ground-like for everything except light; it lives in its own atlas source in `ground_tileset.tres`, a full-tile collision shape on the world physics layer). **Nothing compares that string itself:** every question about it goes through `SurfaceTypes` (`is_ground_like()` (ground and glass), `is_catwalk()`, `is_hangable()` (ground-like or catwalk), `laser_passes()` (catwalk and glass), with `surface_at_cell()`, `surface_at_point()` and `surface_at_hit()` to read a tile's value; the hit version nudges half a pixel into the tile along the inward normal, so a hit on a right or bottom face maps to the right cell). The ledge grab, the catwalk-underside probe, the laser solver, the liquid and steam rays and the basin's floor and wall scans all use it, so a new surface type is added there and nowhere else. Bodies that aren't tiles opt in through the groups `"ground"` and `"catwalk"`, which each caller still tests itself. Ladders live on their **own** `TileMapLayer` (group `"ladder_tilemap"`, no collision — a ladder cell is just "a tile is present there"); a ladder shares its cell with the catwalk it passes through, top flush with the walking surface. One-way platforms use Godot's native `one_way_collision` shape property. The ground TileSet's other custom-data layers are `surf_friction` (float, see Surface friction under Surf) and `hazard_damage` / `hazard_direction` (see Spikes).
- **Audio**: `res://audio/audio.gd` autoload `Audio`. `Audio.play(id, volume_db=0, variant=-1)` (one-shot, non-positional), `Audio.play_at(id, position, ...)` (positional, pooled `AudioStreamPlayer2D`s, `MAX_DISTANCE` 280px for the 2.5x zoom), `Audio.make_loop(id) -> LoopPlayer` (`add_child` it, `.start()`/`.stop_loop()`), `Audio.play_music(id, fade)`/`stop_music(fade)` (two-player crossfade). Ids are `StringName`s scanned from `res://audio/<folder>/<filename>`: lowercased, spaces→underscores, trailing digits stripped and treated as variant number (`player/jump1..5.wav` → id `player/jump` with 5 variants, pitch/volume jitter via `AudioStreamRandomizer`). **A sound whose name legitimately ends in a digit will be misread as a variant of a shorter id** — rename rather than fight it. `music/` ids are the plain filename, no variant handling. Unknown id: silent if listed in `Audio.PLANNED` (called for but no file yet), else one `push_warning`. **Standing rule: a new gameplay element isn't done until its sound hook exists.**

## Level editor seams (stretch goal)

A runtime level editor is a stretch goal with no plan to build it yet. The provisions below keep it possible, so every change from now on should respect them. The first is built (levels load through `Game.load_level()`, see Level loading); the next two are decided when a level can be edited at runtime; the rest are habits to follow whenever the code they concern is touched.

**Built: the loading entry point**
- **One loading entry point that takes a level source** plus a level id: `Game.load_level(id, source)` (a res:// path or a `PackedScene`; null = the catalog's path for the id). Respawn, `restart_level()`, next-level and the pause menu's pick all go through the id and source `Game` remembers, never `scene_file_path`, so a level need not be a file. Level identity is the id: the checkpoint is scoped to it, and `Game.level_root()` replaces `current_scene` wherever "the level" is meant. A custom source (a level assembled from data, a downloaded pack) needs only to produce a `PackedScene`, or a node tree wrapped in one, and an id; ids are permanent once levels are shared. Shared levels must never be `.tscn` files loaded from untrusted sources (a scene can reference scripts): the safe route is a data-only format that names built-in object types, positions and exports.

**Do when a runtime level editor is built**
- **A placed object's identity is its node name.** Snapshot keys are each saveable's path relative to the level root (`Game._key()`), and `PowerTarget.sources` is an `Array[Node]` of node references (stored as paths), so a runtime editor must give every placed object an explicit, unique, stable name (a duplicate added with a bare `add_child()` is auto-named), and renaming or moving an object drops its saved state. `Game.apply()` also frees every saveable with no snapshot entry, so any level edit must clear the checkpoint (`restart_level()` semantics), or a newly placed object would be freed on the next respawn. `PowerTarget.add_source()` works at runtime.
- **Runtime code never writes an export.** Authored values stay exports and anything the game mutates is a separate variable, as `WaterBasin` does (`initial_fill_depth_below_surface` authored, `fill_volume` runtime), so an in-place play-test can return to the untouched level. It is a preference rather than a hard requirement if a play-test always runs a fresh instance of the saved level, as the reload path already does. Audit status, open violations and the re-runnable scan are in `export-audit.md` and `audit_export_writes.py`: update the log whenever you audit or change an object, and fix a listed violation when the object is next touched.

**Habits**
- **Derive-from-level steps are named methods** called from `_ready()`, not inline: the basin's floor sampling, the conductor circuits (built once at load; painted tiles don't rewire today), the gem count, the checkpoint `order` (`_assign_order()` only runs under `Engine.is_editor_hint()`, so a checkpoint placed at runtime would get order 0). An editor can then re-run them after a change.
- **Authoring overlays** (the turret aim preview, wire links, see-saw gizmos) are gated on a flag, not on `Engine.is_editor_hint()`.
- **Configuration warnings are plain methods returning strings**, with `_get_configuration_warnings()` calling them, so a runtime level validator can reuse them.
- **Configuration lives in exports** (the existing pattern), so an inspector can be generated from the property list at runtime.
- **Level format stays `.tscn`.** `PackedScene.pack()` can save at runtime; placed nodes need `owner` set, and generated pieces (the conveyor's pieces, the conductor, finish and see-saw overlays) are all deliberately unowned, so they are never packed. A custom format is only worth it for sharing or hand-edited levels, and the single loading entry point keeps that open.

## Cross-system invariants

One line each; the detail and the reason are in the file named. These are what keep changes in one system from breaking another.

- **Any new player held state, one-shot action or tween must be added to `_interrupt_current_action()`**, or a hit mid-action leaves it dangling (the camera cue is the one deliberate exception). (`player.md`)
- **Code that writes the player's `velocity` stays above the buffered-launch application in `_physics_process()`**, never below it. (`player.md`, Jump pads)
- **Every function that starts a hang sets `hang_style` explicitly**; it is not reset between hangs. (`player.md`)
- **Hard teleports (hang grab, mantle snap, ladder mount) reset physics interpolation on both the player and the camera.** (`player.md`)
- **A resource shared across scene instances (a `Shape2D` on a `CollisionShape2D`) is `.duplicate()`d before it is mutated at runtime.** (`player.md`, Crouch)
- **A new saveable joins group `"saveable"` in its own `_ready()`, never deferred.** `load_state()` is silent (no animation, sound or edge event) and independent of restore order; on anything a power source drives it also tolerates `set_powered_initial()` running afterwards and winning. (`saving-levels-ui.md`)
- **A restore never produces a surprise hit.** A state that could hurt (a hammer swing, an armed mine, a spark drip, an arc) restores harmless or restarts its clock. (`enemies.md`, `lasers-arcs-mirrors.md`)
- **Every new gameplay element has its sound hook, and every id it calls for is in `Audio.PLANNED`** (silent while there is no file). A sound whose name ends in a digit is misread as a variant. (Audio, under Project setup)
- **Layer pairing**: solid world bodies on layer 2; anything the player can kick or bowl through sits on layers 1|2; an `Area2D` never blocks movement. (Physics layers, under Project setup)
- **A body water should rest on or be carried by joins group `"water_solid"`; a new tile surface meaning is added in `SurfaceTypes` and nowhere else.** (Groups in use and Tilemap, under Project setup)
- **The player joins group `"player"` in its own `_ready()`**, so a node that runs earlier finds nothing: look it up again later. (Groups in use, under Project setup)
- **Hazards that must re-hit after i-frames poll `get_overlapping_bodies()` every physics frame** rather than rely on `body_entered`. (`hazards-traps.md`)
- **Every powered device scene has a `PowerTarget` child.** No valid sources means not driven: the device keeps its authored state. (`power.md`)
- **A `MeltableBlock` subclass never overrides `_ready()` or `_physics_process()` without calling `super()`.** (`meltable-blocks.md`)
- **Runtime code never writes an export**: authored values are exports, runtime state is a separate variable. Keep `export-audit.md` current. (Level editor seams)
- **A one-shot `AnimatedSprite2D` animation has Loop off**, or `animation_finished` never fires and the state soft-locks. (`player.md`)

## Checklist: adding a new object type

1. **Place it**: the `.gd` beside its `.tscn`, in the folder that matches its role (`enemies/`, `interactive/`, `traps/`, `collectibles/`, `levels/`, `ui/`; see Project setup).
2. **Layers and masks** (see Physics layers): a new actor masks layer 2, and layer 1 only if it should be solid against other actors; a solid platform or hazard body is layer 2; anything kickable or bowlable is 1|2; a trigger is an `Area2D`.
3. **Groups** (see Groups in use), joined in its own `_ready()`: `"enemy"` for an enemy, `"water_solid"` if water should rest on it, `"laser_mirror"` for a reflector, `"power_source"` or `"power_target"` for the power contract, `"saveable"` if it keeps state across a checkpoint.
4. **Contracts**: implement the duck-typed methods it should answer (table above): `take_damage()` and, if the surf can plough through it, `bowled_over()` for an enemy; `set_powered()` for a device; `is_powered()` and `powered_changed` for a source.
5. **Power**: a device scene carries a `PowerTarget` child and an `invert` export on its root; a source joins `"power_source"`. Add it to Powered devices (or the source's own bullet) in `docs/power.md`.
6. **Save and restore**: if its state changes at runtime, implement `save_state()` and `load_state()` and add it to What each type saves in `docs/saving-levels-ui.md`. A restore must not produce a surprise hit.
7. **Audio**: add the sound hooks and put every new id in `Audio.PLANNED`.
8. **Export audit**: authored values stay exports and runtime state is a separate variable; add the script to `export-audit.md` and run `audit_export_writes.py`.
9. **Level-editor habits** (see Level editor seams): derive-from-level steps as named methods called from `_ready()`, configuration warnings as plain methods, authoring overlays behind a flag.
10. **Document it** (stage 1 of Finishing a roadmap item, under How to maintain this file): a bullet in the matching topic file describing the object as it stands, its name in the docs index, a `## Status` line there until the user confirms it in-editor, then `python3 check_docs.py`. The designer-facing files (`docs/level-design.md`, `docs/puzzles.md`) and the roadmap entry are finished in stage 2, after that confirmation.
